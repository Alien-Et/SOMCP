# 18 · 错误码、数据目录与排障

## 错误信封

所有工具返回统一结构：

```json
{
  "ok": false,
  "error": {
    "code": "APK_INVALID",
    "message": "/data/local/tmp/x.txt is not a ZIP/APK file (magic=74657374)",
    "severity": "error",
    "recoverable": true,
    "retrySameArguments": false,
    "diagnostics": {},
    "argument": "path",
    "badValue": "/data/local/tmp/x.txt"
  },
  "nextActions": []
}
```

`badValue` **只含原始输入**，不再拼接诊断信息。

## 错误码全集

### 输入类

| 错误码 | 含义 | 处置 |
| --- | --- | --- |
| `INVALID_ARGUMENT` | 参数缺失或非法 | 检查参数名与类型 |
| `INPUT_REQUIRED` | 必填参数为空 | 补上参数 |
| `BAD_REQUEST` | 请求体超限或格式错 | 检查 `maxRequestKb` |
| `PATH_NOT_ALLOWED` | 路径含 `..` 穿越 | 用绝对路径 |
| `INVALID_WORK_DIRECTORY` | SAF 工作目录无效 | 重新选目录（通常用不到） |
| `UNKNOWN_ACTION` | 工具或 action 不存在 | 查 `meta_info(describe)` |
| `TOOL_DISABLED` | 工具在禁用列表里 | 检查 `disabledTools` |
| `INVALID_CURSOR` | 分页游标过期 | 重新发起原请求 |

### APK 类

| 错误码 | 含义 | 处置 |
| --- | --- | --- |
| `APK_INVALID` | 不是 ZIP/APK（magic 不匹配） | `message` 里有实际 magic |
| `APK_READ_FAILED` | 读取失败（含 root cat 失败） | 检查路径与 root 授权 |
| `APK_LIMIT_EXCEEDED` | 超过 4 GiB 输入上限 | — |
| `APK_TOO_LARGE_FOR_AUDIT` | 堆余量不足，审计工具拒绝整包读 | 改用 `apk_analyze`（流式） |
| `NOT_ELF_SO` | 文件不是 ELF | 确认路径 / URL |

### ELF 类

| 错误码 | 含义 | 处置 |
| --- | --- | --- |
| `ELF_PARSE_FAILED` | ELF 结构解析失败 | 文件可能被截断 |
| `ELF_CORRUPTED` | 兜底错误（未分类异常） | 看 `message` |
| `NOT_ELF_INPUT` | 输入是 APK/JAR 条目 | 用 `apk_analyze` |
| `INVALID_LOCATOR` | locator 格式不认识 | 查 `acceptedLocatorForms` |
| `OFFSET_OUT_OF_RANGE` | 偏移超范围 | 检查 `offset` / `addr` |
| `LOCATOR_OUT_OF_RANGE` | locator 指向的地址不在任何可读窗口内 | 先用 `translate_address` 判坐标系，再用 `read_hexdump` / `read_disasm` 验证该地址存在；`acceptedLocatorForms` 里列出了可用形态 |
| `INVALID_HEX` | hex 字符串非法 | 检查字符集与长度 |
| `SYMBOL_NOT_FOUND` | 符号不存在 | 先 `analyze_elf(view=list)` |
| `FUNCTION_NOT_FOUND` | 函数不存在 | 先 `analyze_functions` |

### 工作区 / 会话类

| 错误码 | 含义 | 处置 |
| --- | --- | --- |
| `WORKSPACE_REQUIRED` | 缺 `workspaceId` | 先 `so_open` |
| `WORKSPACE_NOT_FOUND` | workspaceId 不存在 | 重新 `so_open`；**注意也会因 LRU 淘汰触发**（常驻上限 8，见下） |
| `EDIT_SESSION_NOT_FOUND` | editSessionId 不存在 | `session_open` |
| `AUDIT_NOT_FOUND` | 审计记录不存在 | 重新 `session_audit` |
| `RESULT_NOT_FOUND` | Blutter 结果不存在 | `flutter_blutter(action=result)` |
| `RESULT_TRUNCATED` | 结果被截断 | 用游标继续 |
| `JOB_NOT_FOUND` | 异步任务不存在 | 重新发起 |

> **`WORKSPACE_NOT_FOUND` 的第二种成因**：`workspaces` 现在有常驻上限
> `MAX_OPEN_WORKSPACES = 8`，`so_open` 成功后按「`temporary` 优先 → 最久未访问」淘汰。
> 淘汰时 `AppLog` 会写一条 `Evicted workspace <id> (<name>)`。
> 所以「刚才还能用的 workspaceId 现在不见了」是**预期行为**，重新 `so_open` 即可。

### 编辑 / 补丁类

| 错误码 | 含义 | 处置 |
| --- | --- | --- |
| `SIZE_MISMATCH` | 汇编结果或选定范围与指令宽度不符 | 见 `badValue`：`alignment` 是要求的整数倍；改用 `instructionCount` 或把 `byteLength` 取成 `alignment` 的倍数 |
| `PATCH_TOO_LARGE` | 单次补丁超过 `maxPatchBytes` | 拆小或调大设置 |
| `ASM_SYNTAX_ERROR` | 汇编文本无法编码 | 检查指令拼写 / 架构 |

**`SIZE_MISMATCH` 的两种典型触发**

```text
选定范围 6B 不是 arm64 指令宽度 4 的整数倍
→ Selected range 6B is not a multiple of the 4-byte instruction size for arm64.
  badValue: {"byteLength":6,"alignment":4}
```

```text
汇编结果比选定范围长（且未指定 instructionCount/byteLength）
→ Assembled code (12B) is larger than selected instruction range (4B).
  badValue: {"assembled":12,"range":4}
```

这是**故意**拦下来的：旧实现会写出半个 NOP（`1F 20 03 D5 1F 20`），
而 build/check 都不校验指令边界，只有目标执行到那段才 SIGILL。

### 执行类

| 错误码 | 含义 | 处置 |
| --- | --- | --- |
| `SERVER_BUSY` | 重型工具闸门已满 | 按 `retryAfterMillis` 重试 |
| `RATE_LIMITED` | 超过每分钟调用上限 | 降低频率 |
| `INSUFFICIENT_MEMORY` | 内存不足 | 关掉其它工作区 / 用流式 |
| `EMULATION_DISABLED` | Unidbg 开关关闭 | 打开 `emulationEnabled` |
| `EMULATOR_UNAVAILABLE` | Unidbg 原生库缺失 | 见 `12.动态分析.md` |
| `RIZIN_CFG_FAILED` | Rizin 配置失败 | 检查 `librz_native.so` 是否 stub |
| `XANSO_BUILD_FAILED` | xAnSo section 重建失败 | 文件可能不是标准 ELF |
| `TOO_MANY_STEPS` | 批量流水线步数超限 | 拆批 |
| `SELF_ANALYSIS_FORBIDDEN` | 试图分析 SOMCP 自己 | 本分支已放行 |
| `WORK_DIRECTORY_NOT_SELECTED` | 需要 SAF 工作目录 | 魔改后极少出现 |

### MCP 传输层 / 工具调度类

这些码**不是引擎返回的**，是 HTTP 服务层或工具调度层自己抛的。引擎层的错误都带
`severity` / `recoverable` / `badValue`，这一层的不一定有。

| 错误码 | 含义 | 处置 |
| --- | --- | --- |
| `TOOL_NOT_FOUND` | 请求的工具名不存在 | 先 `meta_info(action=help)` 或 `tools` 确认名字；`message` 里就是原始名字 |
| `TOOL_EXECUTION_FAILED` | 工具在 `guarded {}` 之外抛异常（未返回统一信封） | `message` 形如 `<异常类>: <消息>`，`hint` 字段会说明这是工具侧缺陷。先看参数是否符合 schema，再 `system_logs` 翻堆栈 |
| `FORBIDDEN_ORIGIN` | `Host` / `Origin` 不是 localhost 或裸 IP | DNS rebinding 防护。局域网客户端用 IP 直连；走域名/反向代理时把 `authEnabled` 打开并走 `Authorization` |

> `TOOL_EXECUTION_FAILED` 与引擎信封里的 `INVALID_ARGUMENT` 区别：前者**没有** `ok:false` 信封
> 结构，只有 `error.code`；后者一律走 `ok:false + error{code,message,severity,...}`。

### Unidbg 模拟执行 / 动态分析类

`dynamic_api` 的 `unidbg_session_*` 系列工具。绝大多数码是「同一套动作在不同工具上复用」，
行为语义见 `12.动态分析.md`。

| 错误码 | 含义 | 处置 |
| --- | --- | --- |
| `LIVE_SESSION_REQUIRED` | 当前没有打开的模拟会话 | 先 `unidbg_session_open`；`message` 里给了期望的工具名 |
| `SESSION_OPEN_ERROR` | 会话打开失败 | `message` 是根因异常文本；常见是输入不是 ELF 或 ABI 不匹配 |
| `EMULATION_DISABLED` | 模拟开关关闭 | 打开 `emulationEnabled` |
| `EMULATION_ERROR` | 模拟通用失败（catch 兜底） | 看 `message` |
| `EMULATOR_UNAVAILABLE` | 模拟所需原生库缺失 | 见 `12.动态分析.md`；本地 debug 包常缺 `libunicorn.so` / `libcapstone.so` |
| `NATIVE_UNAVAILABLE` | 原生后端库缺失 | 同 `EMULATOR_UNAVAILABLE` 的排查顺序 |
| `DUMP_ERROR` | `session_dump` 失败 | 看 `message` / `exception`；`exception` 字段给了异常类名 |
| `MEMORY_MAP_ERROR` | `map` 失败 | 地址要页对齐、范围不能重叠已有映射 |
| `MEMORY_UNMAP_ERROR` | `unmap` 失败 | 确认该区间确有映射 |
| `MEMORY_PROTECT_ERROR` | `protect` 失败 | 目标区间不在已映射范围内 |
| `MEMORY_WRITE_ERROR` | `write` 失败 | 目标地址不可写（权限掩码不含 W） |
| `READ_FAILED` | 内存读返回空 | 地址不在已映射区间 |
| `REGISTERS_ERROR` | 寄存器快照失败 | 先确认会话已 open |
| `MODULES_ERROR` | 模块列表失败 | 目标 SO 未加载成功 |
| `EXPORTS_ERROR` | 导出表读取失败 | 目标 SO 可能 strip 且无动态符号 |
| `CALL_ADDRESS_ERROR` | `call_address` 失败 | 地址非法 / 未映射 / 指令编码失败 |
| `HOOK_ERROR` | `hook_start` / `hook_stop` 失败 | 断点地址不在可执行映射内 |
| `BREAKPOINT_ERROR` | 断点增删失败 | 地址不在可执行映射内；调试器未启动时要先 `hook_start` |
| `DEBUGGER_ERROR` | 调试器状态查询失败 | 检查模拟器是否已 attach |
| `SINGLE_STEP_ERROR` | 单步失败 | 当前在非可执行上下文或调试器未启动 |
| `TRACE_ERROR` | trace 启动 / 停止 / 读取失败 | 检查 `begin`/`end` 区间合法性 |
| `EMU_STOP_ERROR` | 停止模拟失败 | 通常无害（响应已丢失），可重开会话 |
| `STEP_EXCEPTION` | 单步命中了异常 | 正常现象，说明代码执行中抛了异常 |

> 这一层所有码都带 `rootCause(e).message`，直接读 `message` 即可，不需要再 `system_logs`。

### Flutter / Blutter runner 类

| 错误码 | 含义 | 处置 |
| --- | --- | --- |
| `RUNNER_START_FAILED` | runner 进程启动后没有完成就失败 | 响应里的 `detail` 给出 `su` / `am start` 的原始输出；先确认 `files/blutter-engines/` 里存在对应 `dartvm_<ver>.so`（`flutter_blutter(action=engines)` 可查） |
| `FLUTTER_VERSION_NOT_SUPPORTED` | 没有匹配该快照的 Blutter runner | 看响应里的 `missingRunner`：它给出 `dartVersion` / `engineRevision` / `snapshotHash` / `abi` / `compressedPointers`，以及可直接执行的 **`fileName` + `installDirectory`**。把那个 `dartvm_<dartVersion>.so` 放进 `installDirectory`（应用私有目录 `files/blutter-engines/`）后重试即可，**不需要重建 APK** —— 应用自己的 `files/` 可以按绝对路径 `dlopen`。runner 从 `blutter-engines` workflow（`.github/workflows/blutter-engines.yml`）取，或用 `tools/blutter-matrix/build-blutter-runners.sh` 本地构建；`flutter_blutter(action=engines)` 查看目录与已安装项 |
| `RUNNER_INTERRUPTED` | runner 进程中途断开 | 最常见是 Blutter 自身对快照的 Dart 类型编码断言失败（crash log 里形如 `DartTypes.cpp: 330: error: Invalid abstract type`），也可能是被系统按内存回收。主进程不受影响；换用 engine revision 真正命中的快照重试 |
| `RUNNER_CRASHED` | runner 进程在完成前死亡 | 同上，查设备 crash log 的 abort message |
| `RUNNER_BIND_FAILED` | runner 服务未返回 Binder | 服务未安装/被禁用；检查 `:blutter` 进程能否启动 |
| `FLUTTER_LIBS_NOT_FOUND` | APK 内没有完整的 `libapp.so` / `libflutter.so` 对 | 若 so 在设备上的同目录 `lib/<abi>/`（ABI split 安装），现在会自动回退；否则确认 APK 是否为 Flutter 产物 |
| `FLUTTER_INSPECT_FAILED` | 指纹检查失败 | 看 message；非 Flutter APK 属正常结果（`detected:false`） |

## 排障手册

### 服务起不来

1. `system_control(action=status)` 看服务状态
2. 检查端口占用（`PortUtils.isPortAvailable`）
3. 检查 `bindHost`
4. `system_logs` 看环形缓冲

### 客户端连不上

1. 本地验证：
   ```bash
   curl -s -X POST http://127.0.0.1:8000/mcp \
     -H 'Content-Type: application/json' \
     -H 'Accept: application/json, text/event-stream' \
     -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"1"}}}'
   ```
2. 局域网：确认手机 IP 与 `bindHost = 0.0.0.0`
3. 电脑侧：`adb forward tcp:8000 tcp:8000`
4. 开了 token：`Authorization: Bearer <token>` 或 `?token=<token>`

### `RIZIN_UNAVAILABLE`

1. `meta_info(capabilities)` 看 `rizin.status`
2. `meta_info(health)` 看 `librzNative.size`
   - 2.9 MB → stub，需要重建原生
   - 61 MB → 完整
3. 本地重建：
   ```bash
   bash build-native-android.sh
   rm -rf app/.cxx app/build/intermediates/cxx
   ./gradlew :app:assembleDebug --rerun-tasks
   ```

### `EMULATOR_UNAVAILABLE`

1. 看错误消息里的具体缺失库
2. 32 位设备：`libunicorn.so` 本来就不提供，无解
3. 本地 debug 包：`bash build-unidbg-native.sh --abi arm64-v8a`
4. CI 包：应该齐全，若缺说明 workflow 出错

### `so_open` 返回 `SO_NOT_FOUND`

1. `so_open(action=list)` 的返回里有 `rootAvailable`
2. 非 root 时 `/data/data` 无解
3. 非 root 时 `/sdcard` 无解（manifest 无存储权限）
4. `badValue` 只含原始路径，可直接用于重试

### `apk_analyze` 返回 `APK_INVALID`

`message` 里有实际 magic：

```json
"message": "/data/local/tmp/x.txt is not a ZIP/APK file (magic=74657374)"
```

| magic | 判断 |
| --- | --- |
| `504b` | 正常 ZIP |
| `7f45` | ELF（用 `so_open`） |
| `74657374` | 文本 |
| 目录 | `is a directory, not a ZIP/APK file` |

### `apk_analyze` sha256 与 `sha256sum` 不一致

**已修复**（见 `19.变更总览与总结.md` P0-1）。如果还遇到：

1. 确认装的是最新包
2. 对比 `apk_sig_verify` 的 sha256（走另一条路径）
3. 若两者不一致，检查 `NonClosingInputStream` 是否生效

### `APK_TOO_LARGE_FOR_AUDIT`

审计工具需要整包随机访问。堆余量不足时：

- 用 `apk_analyze`（流式，不进堆）
- 或关掉其它工作区释放内存后重试

### 客户端显示「未连接」，但服务端 HTTP 200 一切正常

**先分清两件事**：服务端进程活着 ≠ 客户端的 MCP 会话活着。

排查顺序：

```bash
# 1) 服务端真的在跑吗（这一步过了说明服务没问题）
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://127.0.0.1:8000/mcp \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"p","version":"1"}}}'
# → 200

# 2) initialize 有没有签发会话 id（没有就是服务端 bug）
curl -s -D - -o /dev/null -X POST http://127.0.0.1:8000/mcp \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"p","version":"1"}}}' | grep -i mcp-session-id
# → Mcp-Session-Id: <uuid>

# 3) GET /mcp 是流还是「一条完整响应」
timeout 25 curl -s -D - -N http://127.0.0.1:8000/mcp -H "Accept: text/event-stream"
# 正确：Transfer-Encoding: chunked + 每 10s 一条 ": keep-alive"
# 错误：Content-Length: 75，且连接立刻 EOF → 客户端必然判定掉线
```

**2026-11-08 修掉的两个成因**（见 `02.MCP协议层.md`）：

1. `initialize` 不签发 `Mcp-Session-Id` —— 客户端拿不到会话身份；
2. `GET /mcp` 用 `respondText()` 回了个「完整响应」，SSE 写完就 EOF ——
   客户端把这个 EOF 读作掉线。

另一个常被误判成同一件事的原因是**客户端侧的 App 被系统杀了**（内存吃紧时很常见）：
服务端完全正常，但那个 App 的 MCP 服务没起来，客户端自然连不上。判断方法：
用 HTTP 直接探那个服务自己监听的端口，如果返回
`{"code":403,"message":"MCP server is not enabled"}` 之类，就是对方没开，与 SOMCP 无关。

### 签名冲突

CI release 包签名与本地 debug 包不同，直接覆盖安装会报 `SIGNATURE_CONFLICT`。

用 CI keystore 重签本地包：

```bash
cp app/build/outputs/apk/debug/app-arm64-v8a-debug.apk /tmp/final.apk
$ANDROID_HOME/build-tools/36.0.0/apksigner sign \
  --ks release/somcp-release.jks \
  --ks-pass pass:<store-pass> \
  --ks-key-alias <alias> \
  --key-pass pass:<key-pass> \
  --v1-signing-enabled true --v2-signing-enabled true --v3-signing-enabled true \
  /tmp/final.apk
```

## 三条解析路径的共同行为

### ZIP magic 校验

三条入口都先读 4 字节确认是 ZIP：

```kotlin
if (magicLen < 4 || magic[0] != 0x50.toByte() || magic[1] != 0x4b.toByte()) {
    throw ApkNotZipException(
        "$path is not a ZIP/APK file (magic=${...joinToString("") { "%02x".format(it) }})"
    )
}
```

`ApkNotZipException` 在 `guarded` 里映射成 `APK_INVALID`，
`badValue` 是原始路径，`message` 带实际 magic 值。

**为什么重要**：旧实现 root 分支在 magic 校验之前就 `return` 了，
而 `analyzeRootStream` 自己没校验 —— 传 `.so` / 文本 / 目录 / 空文件
都会返回 `ok:true` + `entryCount:0`，AI 客户端会以为分析成功。

### 全文件 sha256

**这里有一个必须理解的坑**：`ZipInputStream` 读到 central directory
就停了，不会把文件读完。如果直接用 `DigestInputStream` 包住它，
摘要只覆盖「前 N 字节」，而且 N 随内部缓冲预读量漂移 —— 同一个 386MB 包
两次调用会得到两个不同的 hash。

正确做法（现在的实现）：

```kotlin
stream.use { input ->
    val counting = CountingInputStream(input) { n, buf, off -> digest.update(buf, off, n) }
    val buffered = BufferedInputStream(counting, 64 * 1024)
    // ... magic 校验 ...

    // 【关键】ZipInputStream.close() 会关掉它包装的流，用 NonClosing 包装
    val nonClosing = NonClosingInputStream(buffered)
    val replay = SequenceInputStream(ByteArrayInputStream(magic, 0, magicLen), nonClosing)
    ZipInputStream(replay).use { zip ->
        // 遍历条目 ...
    }
    // ZIP 遍历结束后，继续把剩余字节读完
    val tail = ByteArray(64 * 1024)
    while (true) {
        val n = buffered.read(tail)
        if (n < 0) break
        totalRead += n
    }
}
```

`NonClosingInputStream` 覆写 `close()` 为空 —— 否则 `ZipInputStream.use{}`
结束时会把底层 `buffered` 关掉，紧接着读尾部会抛 `Stream closed`。

## 4 个 APK 审计工具

| 工具 | 能力 |
| --- | --- |
| `apk_sig_verify` | v2/v3 签名解析 + digest 重算 + 签名验证 |
| `apk_cert_info` | 证书 subject / issuer / 序列号 / 有效期 / 算法 |
| `apk_zip_anomaly` | ZIP 结构异常（重复条目、越界、非标准压缩） |
| `apk_abi_coverage` | 各 ABI 的 SO 覆盖情况 |

### 字节层四个坑（1.0.24 修复，四个工具此前全部失真）

**① ZIP 条目的 deflate 是 raw deflate，不是 zlib 流。**

`Inflater()` 默认 `nowrap=false`，会去找 2 字节 zlib 头和 4 字节 adler32。
APK 里的条目是 `Inflater(true)`（raw deflate），用默认构造器会抛
`DataFormatException: incorrect header check`，被 `catch` 成 `null` ⇒
**所有压缩条目都读不出来**。后果连锁：

- `apk_abi_coverage` 的 `parsedBytes` 恒 0，`files[]` 里没有 bits/architecture/soname
- `apk_cert_info` 读不到 `META-INF/*.RSA` 兜底证书
- `zipAnomalies` 的 `.so` 4096 对齐检查全部失效

```kotlin
// ✗ val inflater = Inflater()
val inflater = Inflater(true)   // raw deflate
```

**② `2 * 1024 * 1024 * 1024` 声明为 `Int` 会溢出成负数。**

```kotlin
// ✗ 溢出成 -2147483648 → 所有 SO 都被跳过
fun abiCoverage(apk: ByteArray, maxParsedBytes: Int = 2 * 1024 * 1024 * 1024)
// ✓
fun abiCoverage(apk: ByteArray, maxParsedBytes: Long = 2L * 1024 * 1024 * 1024)
```

顺带把「首字节 `0x7F`」的弱判据换成完整 ELF magic（`7F 45 4C 46`），
非 ELF 条目现在明确标 `elfParse:"not_elf"`。

**③ v2/v3 block value 有外层 sequence 长度前缀。**

```text
value = uint32 signersSeqLen | ( uint32 signerLen + signer )*
signer = ( [v3: uint32 minSdk | uint32 maxSdk] ) | uint32 signedDataLen + signedData
         | uint32 signaturesSeqLen + signatures | uint32 publicKeyLen + publicKey
```

旧实现从偏移 0 读长度、把整段当一个 signer，切出来的 signer 起点整体错 4 字节。
`parseSigner` 按错位的长度切完 `signedData` 就正好用尽缓冲区，随后
`q + 4 > signer.size` 成立直接 `return null` —— 这是 `apk_cert_info` 报
`certCount:0`、`apk_sig_verify` 报 `signers:[]` 的唯一原因。

**④ digest / signature 记录是四段式，中间有 `innerLen`。**

```text
digestRecord    = uint32 len | uint32 algId | uint32 innerLen | byte[innerLen] digest
signatureRecord = uint32 len | uint32 algId | uint32 innerLen | byte[innerLen] signature
```

旧实现从 `+8` 切到 `+4+len`，把 `innerLen` 也拼进了数据前面：

- digest 的 `expected` 变成 `20000000c3e6fd76…`（多了 4 字节前缀），与 computed 永不相等 ⇒ 每个签名包都判 `digest_mismatch`
- RSA 签名字节多 4 字节前缀 ⇒ 验签必然 `invalid`

### 算法 ID 常量（易错）

| 名称 | 规范值 | 曾经错写成 |
| --- | --- | --- |
| `CHUNKED_SHA256` | **`0x0103`** | `0x0301`（DSA-with-SHA256） |
| `CHUNKED_SHA512` | **`0x0104`** | `0x0302` |
| `RSASSA-PKCS1-v1_5 with SHA2-256` | `0x0103` | — |
| `RSASSA-PSS with SHA2-256` | `0x0101` | — |
| `ECDSA with SHA2-256` | `0x0201` | — |

v2 规范里 SIG_ALG 与 DIGEST 共用同一套 algorithm id，所以 `0x0103` 既是
`CHUNKED_SHA256` 也是 `RSASSA-PKCS1-v1_5 with SHA2-256`，取决于它出现在
digest 记录还是 signature 记录里。

**签名覆盖范围是裸 signed data**，不加长度前缀。已用 openssl 对真实 APK
双向验证：bare → `Verified OK`，prefixed → `bad signature`。

### SONAME 冲突检测必须按 ABI 分组

同一个库在 arm64-v8a / armeabi-v7a / x86 / x86_64 下大小天然不同。把所有 ABI 的
size 混进一个集合，任何多 ABI 的 APK 都会误报 `soname X maps to multiple sizes`。
真正的冲突是「同一 ABI 内同名 SONAME 却有不同大小」，键用 `"$abi/$soname"`。

### 堆预算保护

这 4 个工具需要**整包随机访问**（ZIP central directory 在文件末尾，
签名块也在末尾）。旧实现一律 `readBytes()` 整包进堆，386MB 包占 386MB 堆。

现在读入前先按真实堆余量检查：

```kotlin
private fun heapHeadroomBytes(): Long {
    val rt = Runtime.getRuntime()
    return (rt.maxMemory() - (rt.totalMemory() - rt.freeMemory())).coerceAtLeast(0)
}

if (declaredSize > heapHeadroomBytes() * AUDIT_MAX_HEAP_FRACTION) {
    return err(
        "APK_TOO_LARGE_FOR_AUDIT",
        "APK is 368 MiB but only 221 MiB of heap headroom is available for a whole-file audit. " +
            "Use apk_analyze (streaming) instead, or free memory and retry."
    )
}
```

`AUDIT_MAX_HEAP_FRACTION = 0.45`。

root-only 路径会先流式落一份临时文件到 `cache/apk-audit/`，读完即删。

## open_url

```text
so_open(action="open_url", url="https://.../libfoo.so", outputName="libfoo.so")
```

流程：

1. URL 白名单：拒绝 loopback / link-local / site-local / multicast
2. 只允许 `http` / `https`
3. 下载上限 8 GiB（`soDownloadMaxBytes`）
4. 校验下载内容是 ELF（4 字节 magic）
5. 落盘：
   - 有 SAF 工作目录 → 写工作目录
   - **没有 → 写 App 外部私有目录 `files/downloads/`**

第 5 步是本分支的修复：旧实现强制要求 SAF 工作目录，而工作目录 UI
已经删了，`open_url` 永久不可用。

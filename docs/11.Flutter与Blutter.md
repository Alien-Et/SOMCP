## 两条能力

| action | 作用 | 依赖 |
| --- | --- | --- |
| `inspect` | 识别 Flutter APK、提取版本指纹、列出 assets | 纯 Kotlin |
| `analyze` | 完整 Blutter 分析（Dart 类/方法恢复） | 内置 Runner |

## inspect：清单与指纹

```text
flutter_blutter(action="inspect", path="/path/to/app.apk")
```

流程：

1. 用 `ZipFile` 只读 central directory（不解压任何条目）
2. 找 `lib/<abi>/libapp.so` + `libflutter.so` 配对
3. 选 ABI（`arm64-v8a` > `x86_64` > `armeabi-v7a` > `x86`）
4. 如果有配对，提取两个库到 scratch 目录并计算快照指纹

返回：

```json
{
  "path": "...",
  "flutter": {
    "detected": true,
    "mode": "aot",
    "requestedAbi": "auto",
    "supportedAbis": ["arm64-v8a"],
    "assets": ["assets/flutter_assets/AssetManifest.json", ...],
    "candidates": [{"abi": "arm64-v8a", "libappEntry": "...", "libappSize": 12345678, "complete": true}]
  },
  "selected": {"abi": "arm64-v8a", "libappEntry": "...", "libflutterEntry": "..."},
  "selectedAnalysis": { /* 快照指纹 */ },
  "entryCount": 14473,
  "limitations": [...]
}
```

### 快照指纹

从 `libapp.so` 里读 Dart 快照的元信息：

- `SNAPSHOT_HASH_OFFSET = 20`（Dart 快照头里的 hash 位置）
- `SNAPSHOT_HASH_BYTES = 32`
- `SNAPSHOT_FLAG_BYTES = 288`

`engineRevision` / `dartVersion` / `snapshotHash` / `compressedPointers`
用于匹配兼容的 Blutter Runner。

## 内存策略

Flutter APK 常 100-500 MB，`libapp.so` 单独可 100 MB+，Dart 快照只能作为
**一整块连续 buffer** 反序列化。所以：

| 操作 | 策略 |
| --- | --- |
| APK 清单 | `ZipFile`，只读 central directory |
| 提取库 | 流式写到文件，边写边算 hash，峰值堆 = 1 个 64 KiB buffer |
| ELF 解析 | `ByteView` 对文件做只读 `mmap`，页是 file-backed，内核可回收 |

旧实现是 `File.readBytes()` 整包 + 每个 section `slice()` 成新数组 +
`.rodata` 解码成 String 跑两个正则 —— 200MB 的包约 600MB 瞬时堆。

## root-only 路径支持

旧实现只认 `File.isDirectory` / `File.isFile`。root-only 路径
（`/data/data` 私有、权限 000/600）**stat 成功但 `open()` 会 EACCES**，
此时 `isFile` 仍为 `true`，旧条件判不到，会掉进 else 分支报 EACCES。

现在的判定：

```kotlin
val needsStage = !file.isDirectory && (!file.isFile || !file.canRead())
val staged = if (needsStage && RootShell.isAvailable()) {
    stageFlutterInput(path, File(context.cacheDir, "flutter-inspect").apply { mkdirs() })
} else null
```

`stageFlutterInput` 用 `RootShell.openStream(path, size)` 流式落一份副本到
`cache/flutter-inspect/staged-*.apk`，`finally` 里删除。

## analyze：Blutter Runner

```text
flutter_blutter(action="analyze", path="...", abi="arm64-v8a", noAnalysis=false)
```

流程：

1. `prepareInput` 解析输入（APK / 目录 / root-only）
2. `BlutterRunnerRegistry.select(requirement)` 匹配 Runner
3. `embedded.cacheKey(...)` 查缓存
4. 命中则直接返回，未命中则跑 `BlutterRunnerService`
5. 结果存 `BlutterResultStore`

### Runner 匹配

```kotlin
data class BlutterRunnerRequirement(
    val engineRevision: String?,
    val dartVersion: String?,
    val abi: String,
    val compressedPointers: Boolean,
    val analysis: Boolean,
    val snapshotHash: String?
)
```

内置 Runner 覆盖 **Flutter 3.44.2 – 3.44.7 / Dart 3.12.2 arm64**。
其他版本返回明确的不支持信息，不会瞎跑。

### 异步任务

`analyze` 立即返回 `jobId`，后续用：

```text
flutter_blutter(action="status", jobId="...")
flutter_blutter(action="result", jobId="...", kind="classes|methods|objects", limit=1000, cursor="...")
flutter_blutter(action="cancel", jobId="...")
```

### 结果存储

`BlutterResultStore` 落点在：

```
/data/user/0/com.soreverse.mcp/no_backup/blutter/v1/
  ├── jobs/<jobId>/          # 输入（libapp.so / libflutter.so）
  └── results/<cacheKey>/    # 输出（classes / methods / objects）
```

`no_backup` 不进云备份，不会被系统 `cache` 清理机制清掉。
`flutter_blutter(action="prune")` 可清理过期结果。

### 原生桥

`blutter/` 里两个文件：

| 文件 | 作用 |
| --- | --- |
| `NativeBlutterBridge.kt` | `System.loadLibrary("blutter_bridge")` 的 Kotlin 包装 |
| `BlutterRunnerService.kt` | 前台服务，跑 Blutter 并回写进度 |

`cpp/blutter_bridge.cpp` 导出：

```kotlin
fun run(
    libraryName: String,
    libappFd: Int,
    libflutterFd: Int,
    resultFd: Int,
    optionsJson: String,
    cancellationToken: Long

```

用 **fd 而不是路径**传参，这样 root-only 的临时副本也能直接喂给 native 层，
不需要额外权限。

## inspectFlutterFromEntries

给流式 root 路径用的轻量版本：调用方已经有条目清单（来自 `ZipInputStream`），
直接基于清单做 Flutter 判定，避免为了一个 `detected` 布尔值再开一次 root 流。

```kotlin
fun inspectFlutterFromEntries(entries: JSONArray, path: String): JSONObject
```

注意：`assets` 列表受 `entryLimit` 限制（只统计返回窗口内的条目）。

## 元数据里的 `"null"` 陷阱

Blutter runner manifest 的字段（`engineRevision` / `dartVersion` / `snapshotHash` /
`reason`）读出来之后要参与「版本匹配」判断。这里有一个 Android `org.json` 的坑：

```kotlin
item.optString("engineRevision")   // 值为 JSONObject.NULL 时返回字符串 "null"（不是 null！）
```

所以 `optString(k).takeIf { it.isNotBlank() } ?: continue` 这类写法**兜不住 null** ——
`"null"` 不空白，会被当成一个真实的版本号继续参与匹配，甚至写进提示里。

本分支统一改用 `core/JsonText.kt`：

```kotlin
item.optNonBlankText("engineRevision")   // 缺失 / JSON null / 空串 → null
```

`coverageHints`、`BlutterRunnerManifest`、`BlutterCoordinator` 的 `flutter.*`、
`BlutterResultStore.prune` 的 `resultKey` 全部已收敛。

## runner 进程：为什么它以前完全跑不起来

`flutter_blutter(action=analyze)` 依赖一个**独立 runner 进程**：主进程把
`libapp.so` / `libflutter.so` 以 fd 传进去，runner 在 `:blutter` 进程里
`dlopen("libblutter_<compatibilityKey>.so")` 并调用 `blutter_run_fd`。

这条链路此前**在任何设备、任何 APK 上都 100% 失败**，是两个叠加的问题。

### ① 进程启动即崩（已修）

`BlutterRunnerService` 原先声明为 `android:isolatedProcess="true"`。隔离进程里
`UserManager` 不可用，Android 禁止访问 SharedPreferences —— 而
`SoReverseApplication.onCreate()` 无条件构造 `SettingsStore(context)`，后者第一件事
就是 `getSharedPreferences()`：

```text
java.lang.IllegalStateException: SharedPreferences cannot be accessed if UserManager
  is not available. (e.g. from inside an isolated process)
    at com.soreverse.mcp.core.SettingsStore.<init>(SettingsStore.kt:25)
    at com.soreverse.mcp.SoReverseApplication.onCreate(SoReverseApplication.kt:28)
```

进程约 0.85 秒死亡，上层只看到 `RUNNER_CRASHED`。
现在 `SoReverseApplication.onCreate()` 开头有 `if (android.os.Process.isIsolated()) return`。

### ② 隔离进程里 runner 仍然 SIGSEGV（已修：改为普通独立进程）

跳过 Application 初始化后 runner 能加载执行了，但在 `blutter_run_fd` 入口附近
SIGSEGV（`fault addr 0xffffffffffffffff` —— 典型的 mmap/read 返回 -1 未校验）。
根因是**隔离进程的 SELinux 域几乎不允许正常工作所需的系统访问**。

`android:isolatedProcess="true"` 因此被移除，runner 现在是普通 `:blutter` 独立进程：

| | 隔离进程（旧） | 普通独立进程（现在） |
| --- | --- | --- |
| UserManager / SharedPreferences | ❌ 不可用 | ✅ |
| runner 能否正常执行 | ❌ SIGSEGV | ✅ |
| 崩溃是否影响主进程 | ✅ 不影响 | ✅ 不影响（独立进程） |
| uid 级安全隔离 | ✅ 独立 uid（如 99040） | ❌ 同 uid |

权衡：runner 是随 APK 一起编译、签名的**可信代码**，服务 `exported=false`，只有同应用可调用。
保留"独立进程崩溃不影响主进程"，放弃 uid 级隔离。

修好后 runner 会真正执行，然后在 **Blutter 自己的 Dart 类型解析**上结束：

```text
abortMessage: '.../blutter/src/DartTypes.cpp: 330: error: Invalid abstract type'
```

这是 Blutter 上游对某些 Dart 3.x 类型编码的支持缺口 —— 匹配是**正确**的
（ProxyPin 的 `snapshotHash` 与 runner 完全一致），失败发生在解析阶段。

## ABI split 安装的 APK

Play / 各类安装器常对 Flutter 应用做 ABI 拆分：`base.apk` 里只剩 DEX 与资源，
`libapp.so` / `libflutter.so` 进了 split APK，设备上则位于**同一个安装目录**的
`lib/<abi>/` 下。按 `base.apk` 分析会误报 `FLUTTER_LIBS_NOT_FOUND` —— 即便 so 就在旁边。

现在会自动回退到同级目录：

```text
/data/app/~~xxx/<pkg>==/base.apk             -> 里面没有 lib/
/data/app/~~xxx/<pkg>==/lib/arm64/libapp.so  -> 自动改用这里
```

注意安装目录里的 ABI 名是 **cpuAbi 简称**（`lib/arm64`、`lib/arm`），
与 APK 内部的 `lib/arm64-v8a` 不同 —— 两种写法都会尝试。

## 版本覆盖，与"增量支持所有 Flutter"

内置 runner 只有 **1 个**：Flutter 3.44.2–3.44.7 / Dart 3.12.2 / arm64-v8a。
实测设备上 10 个 Flutter 应用（抽样 6 个）**命中率 0**：

| 应用 | Dart | 结果 |
| --- | --- | --- |
| 某 Flutter 应用 | 3.11.5 | 不匹配 |
| CloudX / FlClash / Kelivo | 3.13.5 | 不匹配 |
| 木木试衣间 | 3.13.7 | 不匹配 |
| ProxyPin | 3.12.2 | 匹配 ✅（但 Blutter 解析 abort） |

### 兼容单位是 snapshotHash，不是 Flutter 版本

`BlutterRunnerMatcher` 按证据强弱三级打分：

| 分 | 依据 |
| --- | --- |
| 4 | `snapshotHash` 命中（快照格式真正的绑定键） |
| 3 | `engineRevision`（主值或 `engineRevisions[]` 任一项） |
| 1 | `dartVersion`（最弱信号） |

一个 hash 覆盖多个 Flutter 版本（样本的 `78da37fe…` 同时命中 3.41.0 / 3.41.1 / 3.41.2），
所以**需要构建的 runner 数量远少于版本总数**。

### 为什么不能运行时下载缺少的 runner

runner 通过 `dlopen("libblutter_<key>.so")` 加载，走 linker 的 namespace 搜索 ——
**只能命中 APK 的 native lib 目录**。Android 10+ 禁止从可写目录 dlopen/exec，
所以 runner 无法下载到私有目录再加载。

三条可行路径：

1. **按需构建**（推荐）：用 CI 为目标 Flutter 版本构建带对应 runner 的 APK。
   诊断已经能直接驱动这件事：`FLUTTER_VERSION_NOT_SUPPORTED` 现在带
   `missingRunner`（dartVersion / engineRevision / snapshotHash / abi / compressedPointers）。
2. **多产物**：同时发布"精简版（1 runner）"和"全量版（N runner）"，用户按需选。
3. **合并 runner**：把多个版本的解析器合并进一个 `.so`，按 hash 分发 ——
   一个 APK 支持多版本，代价是体积（每个 runner 都是完整的 Dart VM 解析器）。

### 已知限制

- 新版本构建（Dart 3.13.x）的 `libapp.so` **不再导出 `_kDartVmSnapshotData`**，
  `snapshotHash` 提取为 `null`，兼容判断退化到 `engineRevision` / `dartVersion`。
- 微信的 `libapp.so` 报 `APK_INVALID: libapp.so is not an ELF file`（非标准封装），工具正确拒绝。
- `snapshotHash` 匹配 ≠ 解析一定成功：Blutter 仍可能因 Dart 类型编码 abort。

## Dart AOT 在通用 SO 工具下的边界

没有匹配 runner 时，`libapp.so` 仍可用通用 ELF 工具分析，但能拿到的东西有限
（以某 Flutter 应用 27.6MB `libapp.so` 实测）：

| 能做 | 不能做 |
| --- | --- |
| ELF 结构（11 节；`.rodata` 10.6MB、`.text` 18.3MB） | `search_strings("vip")` → 0 命中（Dart 字符串非明文连续存储） |
| **Dart 快照指纹**：`_kDartVmSnapshotInstructions` / `_kDartIsolateSnapshotData` / `_kDartSnapshotBuildId` + build id + flags | `analyze_functions` 为空（Rizin 识别不出 Dart 函数） |
| 证据与 `flutter_blutter(inspect)` 一致 | `read_disasm` 在 `.text` 起始全是 `udf`（Dart stub 区） |

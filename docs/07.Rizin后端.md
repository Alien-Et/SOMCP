# 07 · Rizin 后端

## 反汇编文本的一处上游缺陷与本地补偿

内嵌 Rizin 的 ARM64 后端在做**寄存器别名替换**时用的是朴素子串替换：`x29`→`fp`、
`x30`→`lr`。它不区分「寄存器操作数」与「立即数 / 地址」，于是同形子串被一起改掉：

| 真实指令（字节级复核） | 被腐蚀的输出 |
| --- | --- |
| `stp x29, x30, [sp, #0x30]`（`FD 7B 03 A9`） | `stp fp, lr, [sp, 0lr]` |
| 含 `0x29xx` 的立即数 / 地址 | `0fpxx` |

`read_disasm` 与 `rizin_api(action=disasm)` 两个出口都会带上这个腐蚀（都走 Rizin 文本）。

**补偿**：`EngineRuntime.cleanDisasmLines()` 在清洗阶段按同一映射反向修回 ——
`0lr`→`0x30`、`0fp`→`0x29`。这两串在合法 ARM64 文本里不可能出现（`l`/`p`/`r` 都不是
十六进制数字），所以直接替换是安全的。修复后同一函数正确显示 `[sp, 0x30]`。

> 这是本地补偿，不是上游修复：换 Rizin 版本时应重新验证该现象是否仍存在。

## 反编译器的致命信号与崩溃守卫

`read_disasm` 取伪代码时会执行 Rizin 的 `pdg`（Ghidra 反编译）。当 Ghidra 对某个
函数产出空结果时，`libcore_ghidra.so` 会在 `rz_core_annotated_code_print` 里解引用
空 `RzAnalysisAnnotatedCode`，实测崩溃栈：

```text
#00 rz_core_annotated_code_print+432    librz_core.so
#01 libcore_ghidra.so
#09 RizinNativeEngine_rzDecompile+6920  librz_native.so
signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x0000000000000730
```

**JVM 的 try/catch 抓不到 native 信号**：这一下会把整个 MCP 进程杀掉，客户端看到的是
`ECONNREFUSED 127.0.0.1:8000`，必须重启 App。

`rizin_core.cpp` 因此在 `pdg`/`pdd` 外面包了一层守卫：

| 部件 | 作用 |
| --- | --- |
| `crashHandler`（`SA_SIGINFO`） | 只在 `tlsCrashArmed` 的线程上 `siglongjmp`；其余情况恢复旧 handler 并 `raise`，tombstone 不受影响 |
| `runGuarded(fn)` | 用 `sigsetjmp`/`siglongjmp` 包住一次 native 调用，捕获 `SIGSEGV`/`SIGBUS`/`SIGILL`/`SIGFPE` |
| `installCrashHandlerOnce()` | 首次使用时安装一次，`SA_NODEFER` + `SA_ONSTACK`（允许处理期间再次陷入、且不占用已耗尽的线程栈） |
| 崩溃后的 `cleanupCore` | 也在守卫内执行：半释放的 `RzCore` 树可能二次崩，宁可漏一个 core |

命中时返回 `DECOMPILER_CRASHED` + `signal` 字段，进程继续服务；`strict=false`
的调用方（`read_disasm` 的伪代码块）把它当普通错误字段处理，不影响反汇编主体。

对应源码：`engine/EngineRuntimeBackendRizin.kt`、
`app/src/main/cpp/rizin_core.cpp`、
`nativecore/NativeEngine.kt`（`RizinNativeEngine` 部分）

## 14 个 JNI 导出

`rizin_core.cpp` 导出到 `com.soreverse.mcp.nativecore.RizinNativeEngine`：

```text
rzSelfTest        rzAnalyze         rzFunctions       rzCfg
rzXrefs           rzDisassemble     rzAssemble        rzCommand
rzSearchBytes     rzScanCrypto      rzEsilStep        rzDiff
rzConfigureGhidra rzDecompile
```

`rzSelfTest` 是关键：它在 `System.loadLibrary` 之后立刻跑一遍自检
（设置 `asm.arch = arm` + 解码一条 ARM 指令）。失败时
`meta_info(capabilities)` 的 `rizin.status` 会标成
`failed: ...`，而不是假装可用。

## `rzFunctions` 的 JSON 拼装（1.0.30 修复）

`rzFunctions` 要把整个函数表拼成一段 JSON 交给 Kotlin 的 `JSONArray`
解析。这里有两个曾经踩过的坑，改动前务必读一遍：

**不要用固定大小的缓冲区。** 旧实现是

```c
char b[512];
snprintf(b, sizeof b, "{\"name\":\"%s\",\"addr\":%llu,...}", name, ...);
```

单个函数超过 512 字节就被截断，整段数组随之非法 —— 而 Kotlin 侧只看到
「JSON 解析失败」，于是静默降级成 LIEF 导出符号（`calls` 全 0）。
函数越多的库越容易踩到（实测 36 个函数的库正常，442 和 1390 个的全失败），
所以这个 bug 在小样本上测不出来。现在用 `std::string` 动态拼接：

```cpp
out += "{\"name\":\"";
out += escJson(name);
out += "\",";
out += numBuf;
out += "}";
```

**`escJson` 必须校验 UTF-8。** JNI 的 `NewStringUTF` 遇到非法 UTF-8 会返回
null，一个坏符号名就能毒死整份 payload。现在的 `escJson` 保留合法多字节序列，
把非法字节替换成 `\ufffd`。

Kotlin 侧（`EngineRuntimeBackendRizin.rzFunctions`）在解析失败时不再只写
一句「could not be parsed」，而是带上 `nativePayloadChars` 与 payload 头部
120 字符 —— 下次一眼能看出是截断还是编码问题。

## 构建产物与常见坑

`librz_native.so` 是通过 `--whole-archive` 把 27 个 `librz_*.so`
静态链接进去的，体积巨大：

| 构建类型 | `librz_native.so` 大小 |
| --- | --- |
| 完整构建（CI） | 64,344,368 字节（61 MB） |
| 空 stub（submodule 缺失） | 2.9 MB |

**判断 APK 里是不是真 Rizin**：查 `librz_native.so` 大小。2.9MB 就是
stub，运行时 `RIZIN_UNAVAILABLE`。

### Gradle CMake 缓存坑

改完 `third_party/rizin-src` 后重编，如果只删 `app/build/intermediates/cxx`
是**无效的** —— CMake configure 指纹没变，会直接链接旧的 stub 目标。

必须删 `app/.cxx` 才能彻底重建：

```bash
rm -rf app/.cxx app/build/intermediates/cxx
./gradlew :app:assembleDebug --rerun-tasks
```

### rizin-build 产物不在 git 里

`rizin-build/`（5.5 GB）和 `third_party/rizin-src/` 都在 `.gitignore` 里。
换机器或清缓存后必须重新跑：

```bash
bash build-native-android.sh
```

否则 CMake 检测不到 `rizin-build/<abi>/librz/util/librz_util.a`，
会 fallback 到 `rizin_stub.cpp`，产出 2.9MB 的空 stub。

### 版本由 CI 自动取最新

四个构建类 workflow（`build.yml` / `release.yml` / `test-v11.yml` / `blutter-engines.yml`）在 clone 前用：

```bash
git ls-remote --tags --sort=-v:refname https://github.com/rizinorg/rizin.git \
  | grep -oE 'refs/tags/v[0-9]+\.[0-9]+\.[0-9]+$' | head -1
```

自动取最新的 `vX.Y.Z` release tag，不再 pin 死版本。

## search_bytes 的四种写法

```text
5F2403D5          # Rizin 紧凑 hex
5F24..D5          # nibble 通配符，. 表示任意半字节
5F2403D5:FFFF00FF # bytes:mask
5F 24 ?? D5       # MCP 兼容写法，会规范化为 5F24..D5
```

返回的 hit 包含：

```json
{
  "addr": "0x1234",
  "hexAddr": "0x1234",
  "fileOffset": 4660,
  "section": ".text",
  "sectionOffset": 1024
}
```

可直接衔接 `read_hexdump` 或 patch 工具。

## rz-ghidra 反编译

`decompile` 需要 `libcore_ghidra.so`（CI 构建时会编译 `rz-ghidra` 插件）。
缺失时返回明确的不可用错误，不会静默返回空。

**已知上游缺陷**：Ghidra 对某些函数产出空结果时，插件不检查返回值就把空
`RzAnalysisAnnotatedCode` 交给 `rz_core_annotated_code_print`，在那里解引用
`+0x730` 崩掉。这不是本项目的代码，但**后果由本进程承担**，所以用上面的崩溃
守卫把它变成 `DECOMPILER_CRASHED`。修上游需要改 `rz-ghidra` 的
`RizinArchitecture`/`RizinPrintC`，目前选择隔离而不是 fork 插件。

## rzCommand 的安全边界

`rizin_api(action=command)` 是受控的 raw command 通道：

- 只读命令直接执行
- **写入、文件、shell、调试器命令需要 `unsafe=true`**
- `unsafe=true` 还要求 MCP 已启用 token 认证（即 `authEnabled=true`）

这样避免了「免 key + 任意 shell」的组合风险。

## 性能特征

| 操作 | 备注 |
| --- | --- |
| `analyze` | 大库（如 `libapp.so` 100MB+）耗时显著，受 `heavyGate` 串行化 |
| `functions` | 依赖 `analyze` 已完成 |
| `disasm` | 支持分页，`disasmLimit` / `disasmMaxBytes` 控制 |
| `decompile` | 最慢，Ghidra 反编译单函数通常 1-5 秒 |

Dart AOT 大库（`libapp.so`）上 Rizin 几乎识别不出函数 —— 这是 Rizin
对 Dart 快照的固有限制，不是 bug。函数导航应该用 `flutter_blutter`。

## c++_static 的原因

```kotlin
cppFlags += listOf("-std=c++17", "-fexceptions", "-frtti", "-Wall", "-Wextra")
// c++_static keeps every self-built .so self-contained
```

加固（VMP / Dex2C）重打包可能把 `libc++_shared.so` 从 `lib/` 里删掉。
此时若 `librz_native.so` 是 `c++_shared` 链接的，`dlopen` 会报
`cannot locate symbol _ZTVNSt6__ndk1...` 直接崩启动。

## ABI 分包

```kotlin
splits {
    abi {
        isEnable = true
        reset()
        include("arm64-v8a", "armeabi-v7a", "x86", "x86_64")
        isUniversalApk = true
    }
}
excludes += setOf("lib/armeabi/**", "lib/mips/**", "lib/mips64/**")
```

NDK 29 已不支持 `armeabi`，universal 包如果带上死目录会导致 Dex2C 步骤
`abortOnError`。

## 签名

`signingConfigs.release` 优先读环境变量（CI 用），fallback 到本地 keystore。

CI 的 5 个 secrets：

| Secret | 内容 |
| --- | --- |
| `KEYSTORE` | base64 编码的 JKS |
| `ALIAS` | key alias |
| `ALIAS_PASSWORD` | key 密码 |
| `PASSWORD` | store 密码 |
| `TM` | 时间戳 / 辅助字段 |

`LRP_API_KEY` 可选（LLM release notes 用）。

keystore 恢复的关键是**去空白**：

```bash
printf '%s' "$KEYSTORE_B64" | tr -d '[:space:]' | base64 -d > release/so-reverse-mcp-release.jks
keytool -list -keystore release/so-reverse-mcp-release.jks ...
```

漏了 `tr -d '[:space:]'` 会 `base64: invalid input`。

## 工具链版本：一处定义，全局引用

三个构建工作流（`build.yml` / `release.yml` / `test-v11.yml`）**必须**用同一套
JDK、Gradle、Android platform、build-tools、NDK、cmake。checks 用 A 版本编译
通过、release 用 B 版本发布，checks 的绿灯就证明不了 release 能构建 —— 这正是
历史上踩过的坑：`test-v11.yml` 少装 Unidbg 与 rz-ghidra 两步时 checks 全绿，
而只有 release 包里带着这两样。

因此每个工作流在**顶层 `env:` 块**里声明一次，下面一律用 `$SOMCP_*`
（`run:` 里）或 `${{ env.SOMCP_* }}`（action 输入里）引用：

| 变量 | 值 | 说明 |
| --- | --- | --- |
| `SOMCP_JAVA_VERSION` | `17` | AGP 8.x 要求 |
| `SOMCP_GRADLE_VERSION` | `9.6.1` | 与 `gradle/wrapper/gradle-wrapper.properties` 一致 |
| `SOMCP_ANDROID_PLATFORM` | `platforms;android-36` | |
| `SOMCP_BUILD_TOOLS` | `build-tools;36.0.0` | |
| `SOMCP_NDK` | `ndk;29.0.14206865` | 同时被 `tools/blutter-matrix/matrix-config.json` 硬 pin |
| `SOMCP_CMAKE` | `cmake;3.22.1` | 必需，见下文「CMake 4.x 兼容」 |
| `SOMCP_GRADLE_DIST_MIRROR` | `https://mirrors.cloud.tencent.com/gradle` | 发行包字节来源，见下文「Gradle 发行包：镜像预置」 |
| `SOMCP_GRADLE_DIST_SHA256` | `9c0f7fae…a32c9e14` | 官方 `gradle-9.6.1-bin.zip` 的 sha256，完整性唯一依据 |

`blutter-engines.yml` 不构建 APK（无 JDK / Gradle / SDK platform），只声明
它真正需要的 `SOMCP_NDK` —— 那个值也必须与三个构建工作流相同，因为它产出的
runner 会被用该 NDK 构建的 APK `dlopen`。

### 守卫：`tools/check-workflow-versions.py`

```bash
python3 tools/check-workflow-versions.py
```

退出码 0 = 一致，1 = 有问题。它查六件事：

1. 每个工作流都声明了它该有的 `SOMCP_*`；
2. `env:` 块之外没有同一版本的硬编码副本（注释里的说明文字不算）——
   包括不许内联镜像 URL、不许在别处粘贴 64 位 sha256；
3. 同名 `SOMCP_*` 在所有工作流里取值相同；
4. 三个构建工作流都必须有且只有一条 `tools/seed-gradle.sh` 调用，
   且不许把 `Retry Gradle provisioning` 那套旧写法加回来；
5. `SOMCP_GRADLE_DIST_SHA256` 必须就是 `SOMCP_GRADLE_VERSION` 对应发行包的
   官方哈希（查表 `GRADLE_DIST_VERSIONED_SHA256`）——「升了版本忘了升哈希」
   在 CI 上会表现为 seed 步骤校验失败，在这里提前一步就红；
6. `tools/ci/` 下每个共享脚本都被它该被调用的工作流调用，且没有被内联回去
   （两张表 `SHARED_SCRIPTS` / `SHARED_SCRIPT_USERS`，详见上一节）。

`test-v11.yml` 的 `Workflow toolchain version consistency` 步骤会跑它，
所以在 PR 阶段就会挡住「某个工作流被单独改了版本」这类回归。

新增一个需要 pin 的版本时，改三处：`tools/check-workflow-versions.py` 的
`PINNED` / `EXPECTED` 两个表、三个工作流的 `env:` 块（保持字节一致）、
以及本节的表格。换 Gradle 版本还要同步 `GRADLE_DIST_VERSIONED_SHA256`。

## Gradle 发行包：镜像预置，不走 setup-gradle 的下载

`gradle/actions/setup-gradle@v4` 拉发行包的链路是：

```text
https://services.gradle.org/distributions/gradle-9.6.1-bin.zip
  --307--> https://github.com/gradle/gradle-distributions/releases/download/v9.6.1/gradle-9.6.1-bin.zip
```

第二个地址是 GitHub 的 release 资产 CDN，**整段时间返回 504**（本机连试三次
全 504，而 `services.gradle.org/versions/all` 同时段 200 正常）。action 自己
只重试两次（约 35 秒）就把 job 判死，整条流水线在我们第一个业务步骤之前就红了
（实测 run 42469477147）。

**「再放一条同样的 setup-gradle 步骤」救不了**：`GRADLE_BUILD_ACTION_SETUP_COMPLETED`
为真时第二步只打印一行提示，但仍然会重新 Provision，打到同一个 504 上（日志里
第二次又是两连 504）。

所以改成自己把包取回来，让 action 无事可做：

```yaml
- name: Seed Gradle distribution from mirror (sha256-verified)
  run: bash tools/seed-gradle.sh "$SOMCP_GRADLE_VERSION" "$SOMCP_GRADLE_DIST_MIRROR" "$SOMCP_GRADLE_DIST_SHA256"
- name: Set up Gradle
  uses: gradle/actions/setup-gradle@v4
  with:
    gradle-version: ${{ env.SOMCP_GRADLE_VERSION }}
```

`tools/seed-gradle.sh` 做四件事：

1. 从 `SOMCP_GRADLE_DIST_MIRROR`（腾讯云）取 zip，失败回落官方地址；
2. 用**仓库里 pin 住的官方 sha256** 校验 —— 不从网络取 `.sha256`，那样等于
   信任同一条投递通道两次。镜像上的字节与官方哈希一致（已实测核对），所以
   镜像只是更快、更少抖动的字节来源，完整性仍由哈希保证；
3. 解到 setup-gradle 自己的安装目录
   `$RUNNER_TEMP/.gradle-actions/gradle-installations/installs/gradle-<v>`，
   并把 `bin/` 追加进 `$GITHUB_PATH`；
4. 跑一次 `gradle --version` 确认报的版本号正确（不只是解压成功）。

之后 action 的 `installGradleVersion()` 第一步 `which gradle` 就命中同版本，
打印 `Gradle version 9.6.1 is already available on PATH. Not installing.`，
一个字节都不会去 `services.gradle.org` 拉；即使 PATH 命中失败，它退到
`locateGradleAndDownloadIfRequired()` 时也只会看到已存在的安装目录而复用。

脚本是幂等的（目标目录里已有可执行的 `bin/gradle` 就跳过下载），sha256 不对
或缺失时**直接失败**而不是降级放行。腾讯镜像不提供 `.sha256` 文件，哈希值取自
`https://services.gradle.org/distributions/gradle-9.6.1-bin.zip.sha256`；
换 Gradle 版本时必须同时更新 `SOMCP_GRADLE_DIST_SHA256`，守卫会拦住只改一半。

## 共享脚本:`tools/ci/`

四个构建工作流原来各自内联同一批 shell 片段。审计之后发现 **7 组真重复，其中 6 组
已经分叉** —— 同一件事在不同工作流里实现不同，意味着 checks 的绿灯证明不了 release
能构建（这正是 `test-v11.yml` 早期少装两份 native 的同类问题）。所以把这批片段抽到
`tools/ci/`：

| 脚本 | 原来几份 | 已存在的分歧 |
| --- | --- | --- |
| `install-build-tools.sh` | 4 | `build.yml` 带 `cmake`，其余三个不带；`blutter-engines.yml` 的包顺序又是另一种 |
| `clone-rizin.sh` | 3 | **只有 `build.yml` 带 3 次重试**，`release.yml` / `test-v11.yml` 是裸 `git clone` |
| `build-unidbg-natives.sh` | 3 | `test-v11.yml` 有 cache-hit 跳过，`build.yml` / `release.yml` 没有 → checks 验的是另一条代码路径 |
| `build-rz-ghidra.sh` | 3 | 同上 |
| `verify-rz-ghidra.sh` | 3 | 三份逐字节相同（唯一无分歧的一组，抽出的收益只是「以后加 ABI 只改一处」） |
| `restore-keystore.sh` / `make-ci-keystore.sh` | 3 | **`test-v11.yml` 缺 `tr -d '[:space:]'`** —— 正是历史上 `base64: invalid input` 那个坑 |
| `verify-apk-signing.sh` | 3 | 三处**各自硬编码 `build-tools/36.0.0`**，是 `SOMCP_BUILD_TOOLS` 的影子副本，守卫抓不到 |

### 不改变构建行为

跳过逻辑用 `--skip-existing` 开关表达，**默认关**（= `build.yml` / `release.yml` 的原行为
逐字节不变），只有 `test-v11.yml` 传开启（它本来就带 `actions/cache`，有这层判断）。
签名参数的两种来源也据此分流：

- 默认读 `$STORE_FILE` / `$STORE_PASSWORD` / `$KEY_ALIAS` / `$KEY_PASSWORD` 环境变量
  （`build.yml` / `release.yml`）；
- `--properties release/keystore.properties` 从文件读（`test-v11.yml` —— fork PR 拿不到
  secrets，四个值换成运行时生成的一次性 CI 密钥，只能落文件）。

`verify-apk-signing.sh` 从 `$SOMCP_BUILD_TOOLS` 推导 apksigner 路径
（`build-tools;36.0.0` → `build-tools/36.0.0/apksigner`），影子副本消失：升
`SOMCP_BUILD_TOOLS` 时签名校验跟着走，不再可能「sdkmanager 装新版、apksigner 用旧版」。

`tools/check-workflow-versions.py` 除版本一致性外还守住这层抽取：每个共享脚本必须在
对应工作流里**被调用**，且不得把脚本内部的特征文本粘回工作流
（`apt-get install\b`、`base64 -d`、`keytool -genkey`、
`bash build-rz-ghidra-android\.sh`、`build-tools/\d+\.\d+\.\d+/apksigner` 等）。
`SHARED_SCRIPTS` / `SHARED_SCRIPT_USERS` 两张表覆盖全部 8 个脚本；删掉调用或内联回去，
`test-v11.yml` 第 10 步立刻红。

### 与 release.yml 的差异

`checks` 只负责「代码能不能构建」，不发布产物，所以它比 `release.yml`
多出 lint / ktlint / 合规 / PR 检查 / 单测，少了 release notes 与上传。
两个工作流的原生构建步骤（Rizin+LIEF、Unidbg、rz-ghidra、Blutter）必须
保持一致 —— 否则 `checks` 全绿也证明不了发布产物可用。历史上就踩过这个坑：
`test-v11.yml` 早期没有 Unidbg 与 rz-ghidra 两步，checks 通过但
`lief_api` / `emulate_*` / `unidbg_*` 在真机上全是不可用。

## Blutter runner 的打包预算

Blutter 的每个 runner 是一个 **约 37.5 MB 的 `.so`**，而 curated 矩阵现在有
11 个 Dart 版本。全部装进 `app/src/main/jniLibs/arm64-v8a/` 就是约 400 MB，
`zipflinger` 在 `ApkFlinger$writeFile` 里 deflate 这些条目时会把 Gradle 堆
（`org.gradle.jvmargs=-Xmx4096m`）撑爆：

```text
Caused by: java.lang.OutOfMemoryError: Java heap space
  at com.android.zipflinger.NoCopyByteArrayOutputStream.<init>
  at com.android.zipflinger.Compressor.deflate
  at com.android.builder.internal.packaging.ApkFlinger$writeFile
  at PackageAndroidArtifact$IncrementalSplitterRunnable.doExecute
```

这不是偶发——只要 runner 真的构建成功就必然发生。所以 runner 的**构建**与
**打包**被拆成两件事，由两个环境变量控制（都在
`tools/blutter-matrix/build-blutter-runners.sh` 里）：

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `BLUTTER_INSTALL` | `1` | `1` 把 staging 里校验过的 `runners.json` + `libblutter_*.so` 装进 `app/src/main`；`0` 只做构建 + staging 校验，`app/src/main` 一个字节都不动 |
| `BLUTTER_MAX_RUNNERS` | `0` | `0` = 不限制（历史行为）；`N` = 最多只把 N 个 runner 装进 APK，其余仍构建并留在 `build/blutter-matrix/` 供 `blutter-engines.yml` 打成按需引擎包 |

三个工作流的取值：

| 工作流 | `BLUTTER_INSTALL` | `BLUTTER_MAX_RUNNERS` | 理由 |
| --- | --- | --- | --- |
| `test-v11.yml`（PR 门禁） | `0` | — | 门禁只需要证明矩阵能编译。它自己还要跑 `assembleDebug` + `assembleRelease`，不该背 400 MB |
| `release.yml`（发布） | `1` | `1` | 发布包只带 1 个 runner（与入库基线一致），避免 OOM；其余走按需引擎包 |
| `blutter-engines.yml`（引擎包） | `0` | `0` | 它的产物就是全部 runner，必须一个不少，且不该改 `app/src/main` |

### 上限怎么选：`generate_manifest.py --max-runners`

裁剪不是「随便留几个」，`select_runners()` 按下面优先级从高到低排：

1. `compatibilityKey` 已在当前入库 manifest 里 —— 重建出来字节一致
2. `dartVersion` 已在当前入库 manifest 里 —— **`compatibilityKey` 里含
   `blutterCommit` 哈希，上游 rebase 一次 key 就全变**，所以版本号才是跨
   rebase 稳定的身份
3. 稳定版优先于 beta
4. Dart 版本从新到旧

第 2 条是必需的：`verify_manifest.py` 把上游 pin 在 `4a60ac648b`，而当前入库的
`runners.json` 是 `528acbe83b` 构建的。若只按 key 匹配，`--max-runners 1`
会挑到最新的 `3.14.0 beta`，把已发布的 `3.12.2` 稳定版悄悄换掉。

被裁掉的 runner 会逐条打印 `not packaged: <runnerId> [<key>]`，不会静默消失。

### SDK 包


## release.yml

在 `build.yml` 基础上多了：

- `Resolve and validate release tag`（第一步，产出唯一的发布标签）
- 缓存原生后端（`Cache native backends`）
- Build Blutter runners（best-effort）
- 生成 release notes（LLM，可 fallback 到 commit 列表）
- 重命名 APK 并生成 `SHA256SUMS`
- `softprops/action-gh-release@v2` 上传

Gradle 的预置方式与 `build.yml` 完全相同（`tools/seed-gradle.sh` → `Set up Gradle`），
两者必须保持一致：发布用的发行包与 checks 用的必须是同一个字节流。

### 资产命名

```bash
VERSION="${{ steps.release.outputs.tag }}"
VERSION="${VERSION#v}"
cp "$f" "release/SOMCP-${VERSION}-${name}.apk"
(cd release && sha256sum SOMCP-*.apk > SHA256SUMS)
```

产物名：

```text
SOMCP-2.0.0-arm64-v8a.apk
SOMCP-2.0.0-armeabi-v7a.apk
SOMCP-2.0.0-x86.apk
SOMCP-2.0.0-x86_64.apk
SOMCP-2.0.0-universal.apk
SHA256SUMS
```

### 标签的唯一来源：本地 `git tag` + `git push`

发布标签**不由工作流决定**。工作流只做两件事：构建、把产物挂到那个已经存在的标签上。

`workflow_dispatch` 只有一个布尔开关，没有自由输入版本号的地方：

```yaml
on:
  push:
    tags: ['v*']
  workflow_dispatch:
    inputs:
      confirm:
        description: '确认：从下方选择的 tag 构建并发布（标签必须已存在）'
        type: boolean
        default: false
```

**为什么改成这样**：早期版本让用户手填 `tag`，留空则退回 `github.ref_name`，
三处引用都是 `${{ inputs.tag || github.ref_name }}`。手动触发时如果没填，
`github.ref_name` 就是分支名 `main` —— 于是真的发布出了一个
`releases/tag/main`，带全套 6 个资产（实测 run 42461395411 之后清理掉的那次）。

现在的 `Resolve and validate release tag` 步骤（在 `Init submodules` 之前，
id 为 `release`）做四层校验，任一不过就红：

```text
1. workflow_dispatch 必须 confirm=true
2. GITHUB_REF_NAME 必须匹配 ^v[0-9]+\.[0-9]+\.[0-9]+$     ← 分支名在这里被挡下
3. refs/tags/$REF_NAME 必须真实存在
4. tag 指向的提交必须等于 HEAD（从 tag ref 重跑，别从别的分支跑）
```

通过后 `echo "tag=$REF_NAME" >> "$GITHUB_OUTPUT"`，后面三处一律引用
`${{ steps.release.outputs.tag }}`：

| 位置 | 用途 |
| --- | --- |
| `Generate release notes with LLM` | `RELEASE_TAG` 环境变量（喂给 LLM 与 fallback 模板） |
| `Rename APKs and generate SHA256SUMS` | `VERSION` |
| `Upload APKs and release notes to release` | `tag_name`（`softprops/action-gh-release@v2`） |

**为什么需要 workflow_dispatch 兜底**：仓库曾经是 fork，fork 期间 tag push
不触发任何 workflow。即使 `Remove fork network` 之后，用 PAT 推的 tag 也可能
不被识别为 push 事件。手动 dispatch 时从 ref 下拉框里挑那个已存在的 tag 即可，
标签本身仍然是本地推上去的那一个，不存在「工作流造出一个标签」的路径。

### 发布说明的版本区间

要求是「上一个版本 → 当前版本之间的提交信息」。取上一个版本不能用 `HEAD~1`：

```bash
# 错：HEAD~1 问的是「HEAD 下面那个提交之前最近的标签」
PREV_TAG=$(git describe --tags --abbrev=0 HEAD~1 2>/dev/null || true)
```

两种情况下它会给出错误答案：

- 打完 tag 之后又落了提交（`HEAD` 不在 tag 上）：`HEAD~1` 返回的**就是当前
  这个 tag**，于是 `$PREV_TAG..HEAD` 只剩下 tag 之后的提交，本版本的内容全丢；
- tag 指向的提交正好是分支第一个提交：直接报错，回落到「最近 50 条提交」。

现在先问「从 HEAD 可达、且不是本次发布那个」的最近版本标签：

```bash
PREV_TAG=$(git describe --tags --abbrev=0 \
  --match 'v[0-9]*.[0-9]*.[0-9]*' \
  --exclude "$RELEASE_TAG" HEAD 2>/dev/null || true)
```

`describe` 只看 HEAD 可达的标签，从旁支切出来的发布可能一个都看不到，
所以再补一层回落：按版本序取最高的另一个 `vX.Y.Z`（版本序保证
`v1.0.10 > v1.0.9`，字典序会反）。两层都为空才是真正的初始发布，
此时 notes 写「本发布说明为初始发布。」并用最近 50 条提交。

区间验证（临时仓库真实跑过）：

```text
场景A HEAD 正好是 v1.0.10     旧 HEAD~1 -> v1.0.9    新 describe -> v1.0.9   一致
场景B tag 之后又落 2 个提交   旧 HEAD~1 -> v1.0.10   新 describe -> v1.0.9
                              旧区间丢掉 release v1.0.10 这条，新区间包含它
场景C 只有一个 tag（初始发布） 新 describe 与回落都为空 -> 走「初始发布」分支
```

### Gradle 增量缓存坑

改完 Kotlin 后 `assembleDebug` 报成功但 dex 里没有新代码 —— 遇到过多次。
**关键验证一律加 `--rerun-tasks`**：

```bash
./gradlew :app:assembleDebug --rerun-tasks
```

验证新代码是否进包：

```bash
unzip -p app/build/outputs/apk/debug/app-arm64-v8a-debug.apk classes3.dex > /tmp/d.dex
grep -qa "新增的字符串常量" /tmp/d.dex && echo OK
```

### CMake 缓存坑

改完 native 代码后如果只删 `app/build/intermediates/cxx`，CMake configure
指纹没变，会直接链接旧的 stub。必须：

```bash
rm -rf app/.cxx app/build/intermediates/cxx
./gradlew :app:assembleDebug --rerun-tasks
```

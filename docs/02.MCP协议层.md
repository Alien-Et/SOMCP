# 02 · MCP 协议层

对应源码：`app/src/main/java/com/soreverse/mcp/mcp/McpHttpServer.kt`

## 传输形态

Ktor CIO HTTP 服务器，Streamable HTTP 传输（协议 `2025-06-18`），同时兼容旧版
HTTP+SSE 传输（`2024-11-05`）。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/mcp` · `/rpc` · `/messages` | JSON-RPC 请求（主通道） |
| `GET` | `/mcp` | **长连接** SSE 流（`Transfer-Encoding: chunked`，10s 一次 `: keep-alive`） |
| `DELETE` | `/mcp` | 终止会话（`204 No Content`） |
| `GET` | `/sse` | 旧版 HTTP+SSE 握手：先 `event: endpoint`，随后保持长连接 |
| `GET` | `/health` | 健康检查（不需要 JSON-RPC 封装） |
| `GET` | `/` · `/.well-known/mcp` | 服务发现 JSON |

JSON-RPC 响应在客户端 `Accept` 里包含 `text/event-stream` 时以单条
`event: message` + `data: <json>` 返回，否则返回 `application/json`。

## 会话与 SSE 流（两处必须遵守的规范细节）

### `Mcp-Session-Id`

`initialize` 的响应**必须**带 `Mcp-Session-Id` 头，客户端在后续每个请求上回传。

```text
POST /mcp  {"method":"initialize", ...}
→ 200 OK
  Mcp-Session-Id: b01f02a3-3da2-4a57-bba6-734cd348690f
  Content-Type: text/event-stream
```

本服务**不保存任何会话状态**，所以这个 id 是身份令牌而非状态句柄。但它仍然必须
被**签发**：拿不到 id 的客户端无法区分「我的会话还活着」和「我的会话已经没了」，
这正是「服务端 HTTP 200 一切正常、客户端却坚持说自己没连上」的成因。

实现见 `McpHttpServer.Sessions`：

| 行为 | 说明 |
| --- | --- |
| 签发 | `initialize` 时生成 UUID；若客户端已带 `Mcp-Session-Id` 则沿用它 |
| 刷新 | 每个带 id 的请求都会刷新其 `lastSeen` |
| 宽松采纳 | **未见过**的 id 直接采纳，不返回 404 —— 本服务不要求 id，把过期 id 变成硬失败没有收益 |
| 淘汰 | TTL 1 小时 + 上限 64 条，超出按最久未用淘汰 |
| 终止 | `DELETE /mcp` 移除该 id |

### `GET /mcp` 必须是**长连接**

这是 MCP 规范里最容易踩的一条：SSE 是流，`respondText(...)` 产出的是**完整响应**
（`Content-Length: 75`）并在写完立刻关闭连接。客户端发这个请求就是为了订阅服务端
推送，拿到瞬间 EOF 会读作「连接掉了」——于是服务端看起来是死的，其实完全健康。

正确做法是 `respondTextWriter(ContentType.Text.EventStream)` 进入循环并周期性
`write(": keep-alive\n\n")` + `flush()`：

```text
GET /mcp   Accept: text/event-stream
→ 200 OK
  Transfer-Encoding: chunked          ← 有 chunked 才是流；出现 Content-Length 就是 bug
  Content-Type: text/event-stream

  : keep-alive
  : keep-alive
  ...
```

keep-alive 间隔 `SSE_KEEPALIVE_MS = 10s`，必须明显小于 CIO 引擎的 idle 超时
（默认 45s），否则流会在两次 tick 之间被回收。并发流数量上限 8
（`maxSseStreams`），超出返回 `503` —— 每条流占一个协程和一个 socket，而设备
被遗弃的流（对端不发 FIN）只会在下一次写 keep-alive 时才被回收。

## 启动与绑定

```kotlin
McpHttpServer(context, port, host)
```

- `port` 来自 `SettingsStore.port`，默认 `8000`，范围限制 `1024..65535`
- `host` 来自 `SettingsStore.bindHost`，默认 `0.0.0.0`（局域网可达），
  可设为 `127.0.0.1`（仅本机 / adb forward）

## 鉴权

```kotlin
private fun authorized(request): Boolean {
    if (!settings.authEnabled) return true       // 出厂默认关闭
    val auth = request.header("Authorization").orEmpty()
    val bearer = auth.removePrefix("Bearer").trim()
    // 也接受 ?token=<token> 查询参数
}
```

- `authEnabled` 出厂默认 **`false`**（本分支改动，上游默认开启）
- 首次安装会执行 `lanNoAuthMigrated_v1` 迁移，强制关闭 token
- 开启时可用两种方式携带 token：`Authorization: Bearer <token>` 或
  `?token=<token>` 查询参数
- 从关闭切到开启时，`SettingsStore` 会自动轮换 `accessToken`，
  使之前泄露的旧 token 立即失效

## JSON-RPC 方法

| 方法 | 说明 |
| --- | --- |
| `initialize` | 握手，返回 `serverInfo` + `_meta`（含 `fullToolCount`、`provenance`） |

## 并发闸门

重型工具（`so_open` / `search_bytes` / `analyze_*` / `read_disasm` 等）受
`Semaphore` 保护：

```kotlin
private var heavyGate: Semaphore = Semaphore(1)   // 默认 1 个 permit
```

- permit 数来自 `SettingsStore.maxConcurrentTools`，可通过
  `reconfigureHeavyGate()` 热更新
- 抢不到 permit 时立即返回：

```json
{"ok": false, "error": {"code": "SERVER_BUSY",
 "message": "Another analysis task is running. Retry the same call shortly."}}
```

- **重要**：`cancel` / `status` / `prune` 类工具**不参与**闸门。否则当
  permit 被长任务占满时，连取消请求都抢不到，无法自救。

## 速率限制

独立的令牌桶，与并发闸门互不影响：

- 阈值来自 `SettingsStore.toolCallRateLimitPerMin`（0 = 不限）
- 超限返回 `RATE_LIMITED`

## 工具调用编排

`tools/call` 的完整流水线：

```
解析 JSON-RPC
  ↓
查 ToolCatalog.byName
  ↓ 找不到 → UNKNOWN_ACTION
  ↓
检查 disabledTools 黑名单
  ↓ 命中 → TOOL_DISABLED
  ↓
速率限制检查
  ↓ 超限 → RATE_LIMITED
  ↓
重型工具抢 heavyGate
  ↓ 抢不到 → SERVER_BUSY
  ↓
ToolStats 计数（可选持久化）
  ↓
handler.invoke(engine, args, workDirectory)
  ↓
截断到 toolResultMaxChars
  ↓
包成 MCP content 信封（isError 由 ok 字段决定）
  ↓
释放 heavyGate
```

## 工具结果信封

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "isError": false,
    "content": [
      {"type": "text", "text": "{\"ok\":true, ...}"}
    ]
  }

```

注意 `content[0].text` 是**字符串化的 JSON**，客户端需要二次解析。

## lean 模式

默认开启（`SettingsStore.leanTools = true`），只广告：

- 全部 `ToolClass.CORE`（28 个）
- 全部 `lowlevel` 网关（11 个，它们是入口而非证据调用，藏起来等于让能力不可达）
- `meta_info`

其余 `ToolClass.EXTRA`（50 个）通过 `meta_info(action=describe)` 按需发现。

`adaptiveLeanTools = true` 时，会根据 `ToolStats` 的历史调用热度自动把高频
EXTRA 工具晋级到 `tools/list`。

## 请求体上限

`SettingsStore.maxRequestKb`（默认 512 KiB）限制单次请求体大小，
超限返回 `BAD_REQUEST`。大 payload（如 `edit_text` 的整段 smali）需要注意。

## 已知限制

- 不支持 MCP 的 `resources` / `prompts` 能力，只有 `tools`
- 不支持 WebSocket 传输
- 单实例：同一端口只能跑一个 `McpHttpServer`

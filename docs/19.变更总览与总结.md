## 一、本分支相对上游做了什么

上游：[bilieebiliee1-design/SOMCP](https://github.com/bilieebiliee1-design/SOMCP)
（AGPL-3.0-only，Copyright (C) 2026 SOMCP authors）

### 1. 定位调整：从「带 UI 的分析器」到「纯 MCP 服务器」

上游有一个内置「分析」Tab、文件浏览器、前端分析面板。本分支全部删除，
App 只做一件事：把 MCP 服务跑稳。所有分析动作由外部 MCP 客户端驱动。

**影响**：App 从「人用的工具」变成「给 AI 用的后端节点」。

### 2. 路径策略：从「SAF 工作目录」到「root 任意路径直读」

上游要求用户通过系统文件选择器授权一个工作目录，所有文件必须在这个目录内。
本分支废除该限制：

| 上游 | 本分支 |
| --- | --- |
| 必须先选工作目录 | 不需要 |
| 只能读目录内的文件 | 有 root 就任意路径 |
| 读受限路径要先复制进工作目录 | `su -c cat` 管道直读，不落盘 |
| 大 APK 一次性 `readBytes()` 会 OOM | 流式解析，386MB 包 21 秒 |

**影响**：可以直接分析 `/data/app/<pkg>/` 下的安装包、`/data/data/<pkg>/` 私有数据、
`/data/local/tmp` 下的样本，不需要任何中间拷贝。

### 3. 访问控制：从「默认要 token」到「默认免 key」

上游 `authEnabled` 默认 `true`，本分支改为 `false` 并加一次性迁移
`lanNoAuthMigrated_v1`。

**影响**：局域网内客户端直接连，不需要 Authorization。需要收紧时可在
「设置 → 访问」打开。

### 4. 删除的功能

| 功能 | 原因 |
| --- | --- |
| 分析 Tab + AnalyzeController + AnalyzeDataAdapter + ElfOverviewPanel | 定位调整 |
| 工作目录 UI + SAF 授权流程 | 路径策略调整（仅 `open_url` 保留兼容） |
| Cloudflare Tunnel 全链路 | 用户明确不需要，且 CI 要花 20 分钟编译 cloudflared |
| 外观设置页 | UI 简化（主题代码保留，只是没有入口） |
| APK MCP 桥接 | 依赖 MT 管理器侧边栏，链路不可控 |
| 崩溃上报 / 日志上报 | 隐私与体积 |
| `DeepReportStore.kt` / `AiTypes.kt` / `ExternalLinks.kt` / `CrashReportActivity` | 死代码 |

### 5. UI 重构（5 轮）

## 二、本分支修掉的具体 Bug

按严重程度排序。每条都写了**现象 → 根因 → 修法**，便于回归验证。

### P0-1 · `apk_analyze` 的 sha256 错误且不稳定

**现象**：同一个 386MB APK 连续调用两次，返回两个不同的 sha256
（实测在 `fd53cae8…` 与 `2bd19f75…` 之间摆动），且都不等于 `sha256sum`。

**根因**：root 流路径用 `DigestInputStream` 包住 `ZipInputStream` 的输入，
而 `ZipInputStream` 读到 central directory 就停了，不会把文件读完。
摘要只覆盖「前 N 字节」，N 还随内部缓冲预读量漂移。

**修法**：ZIP 遍历结束后继续把剩余字节读完再收摘要。
关键技术点：`ZipInputStream.close()` 会连带关掉底层流，必须用
`NonClosingInputStream` 包装，否则读尾部立刻抛 `Stream closed`。

**验证**：连续 4 次全部返回 `b3830a5d…cb48ba`，与 `sha256sum` 一致。

### P0-2 · 非 ZIP 输入返回 `ok:true`

**现象**：传 `.so` / 文本 / 目录 / `/dev/null`，全部返回
`{"ok":true, "entryCount":0}`，AI 客户端以为分析成功。

**根因**：`analyzeApk` 的 root 分支在 magic 校验之前就 `return` 了，
而 `analyzeRootStream` 自己没做校验。

**修法**：三条入口（`analyze` / `analyzeFile` / `analyzeRootStream`）全部
先读 4 字节验 magic，不是 ZIP 抛 `ApkNotZipException`（映射到 `APK_INVALID`），
`message` 里带实际 magic 值。

**验证**：文本 → `APK_INVALID (magic=74657374)`；ELF → `APK_INVALID (magic=7f454c46)`；
目录 → `is a directory, not a ZIP/APK file`；不存在 → `APK_READ_FAILED`。

### P0-3 · `manifest` / `dexFiles` / `parsedBytes` 是假值

**现象**：root 流解析 386MB APK，`manifest.present` 永远是 `false`，
`resourcesArsc` 永远 `false`，`parsedBytes` 永远 `0`，`flutter` 永远空对象。

**根因**：`analyzeRootStream` 里这几个变量声明后从未赋值，只收集了条目名。

**修法**：真实读取 `AndroidManifest.xml` 和 `classes*.dex` 并解析
（DEX 头解出 magic / methodIds / classDefs 等），`resources.arsc` 存在性检查，
Flutter 判定复用已收集的条目清单（`inspectFlutterFromEntries`）。
`analyzeFile` 同步补上。

**验证**：`manifest.present:true`、`resourcesArsc:true`、`parsedBytes:143690824`、
`methodIds` 全部出现。

### P0-4 · `analyzeApk` 对同一文件开两次 root 流

**现象**：每个大 APK 分析要起两次 `su` + 两次 `cat`，第一次读进 pipe 的数据
被直接丢弃。

**根因**：先 `openStream` 探一次（probe），关掉，再让 `analyzeRootStream`
自己 `openStream` 第二次。

**修法**：能直读走 `analyzeFile`，不能直读只开一次 root 流。

**验证**：386MB 包 root 流路径 21 秒（原来约 40 秒）。

### P1-5 · `readBytes` 的超时形同虚设

**现象**：读一个被 FUSE 挂住或 NFS 卡死的文件，MCP 请求永久挂起。

**根因**：`val timeout = ...` 算出来后**从未使用**，`waitFor` 用的是
`defaultTimeoutMs`；而且 `waitFor` 排在「读完 stdout」之后 ——
`cat` 不产出时 `input.read()` 永久阻塞，永远走不到 `waitFor`。

**修法**：看门狗定时器到点直接 `destroyForcibly()`，让阻塞的 read 抛
`IOException` 返回。同时 `stderr` 由守护线程抽干（否则 `cat` 写满 64KB
pipe 后与 App 互等死锁）。

### P1-6 · `openStream` 不检查退出码

**现象**：`cat <目录>` / `cat <不存在文件>` 返回「非 null 但立即 EOF」的流，
上层无法区分「空文件」和「读取失败」。这是 P0-2 的成因之一。

**修法**：读到 EOF 时校验子进程退出码，非 0 抛 `IOException` 并带上 stderr。
新增 `expectedSize` 参数，`cat` 中断导致字节数偏少时明确报「截断」。

**验证**：目录 → `is a directory, not a ZIP/APK file`；
不存在 → `root cat failed ... (exit=1): cat: ... No such file or directory`。

### P1-4 · `open_url` 永久不可用

**现象**：`so_open(action=open_url)` 永远返回 `WORK_DIRECTORY_NOT_SELECTED`。

**根因**：强制要求 SAF 工作目录，而工作目录 UI 已经删了，`treeUri` 永远是 null。

**修法**：没有工作目录时落到 App 外部私有目录 `files/downloads/`
（不需要任何存储权限）。

**验证**：错误码变成 `NOT_ELF_SO`（说明下载流程真的执行了）。

### P2-7 · 首页 Root 卡 1Hz 轮询

**现象**：一天 86,400 次 `su -c id` fork（单次约 25ms），烧电、刷爆 KernelSU 日志、
息屏后照跑。

**修法**：降到 30 秒一次。「重新检测」按钮可立即重测。

### P2-8 · `badValue` 被污染

**现象**：`badValue` 返回 `"/data/local/tmp (root available=true)"`，
任何程序化处理该字段的地方都拿到非法路径。

**根因**：异常消息里拼了诊断信息，`guarded` 用
`substringAfter(": ")` 当 badValue。

**修法**：异常消息只带原始路径；`guarded` 兜底再剥离一次括号（兼容老格式）。

### P2-9 · 4 个 `apk_*` 审计工具整包进堆

**现象**：386MB 包直接占 386MB 堆，`MemoryGuard` 是 no-op，超限就
`OutOfMemoryError`。

**修法**：读入前按真实堆余量检查（`AUDIT_MAX_HEAP_FRACTION = 0.45`），
放不下返回 `APK_TOO_LARGE_FOR_AUDIT` 并建议改用流式 `apk_analyze`。
root-only 路径先流式落临时文件到 `cache/apk-audit/`，读完即删。

**验证**：368MB 包返回「only 221 MiB of heap headroom is available」。

### 第二轮全项目扫描（2026-11-07）

第一轮的 9 个 bug 修完并验证后，又做了一次全项目静态扫描，找出 9 个新问题；全部已修并实测。

| 编号 | 位置 | 是什么 | 影响什么 | 修法 |
| --- | --- | --- | --- | --- |
| B1 | `PatchByteUtils.repeatBytes` / `EngineRuntimeEditPatch` | 用 NOP 填充「不是指令宽度整数倍」的范围时，末尾会写入半个指令（arm64 给 `byteLength=6` 会产出 `1F 20 03 D5 1F 20`） | 产出**非法编码**；`edit_check` / `build` 都不校验指令边界，只有目标真的执行到那段才 SIGILL 崩溃，排查成本极高 | `repeatBytes` 加 `require(length % step == 0)`；`edit_asm` 写入前用 `instructionAlignment(nop)` 拦截，返回 `SIZE_MISMATCH` + `badValue{alignment}` |
| B2 | `EngineRuntime.workspaces` | `ConcurrentHashMap` **无上限**，只有 `so_close` 才 remove；同文件的 `searchCache`（>64 清理）、`PageStore`（max 64）都有保护，唯独它没有；`MemoryGuard` 又是 no-op | 连续 `so_open` 多个大 SO 会常驻到进程结束，最终 `OutOfMemoryError` 把 MCP 服务进程干掉（用户侧表现为「SOMCP 开着开着没响应了」） | 新增 `MAX_OPEN_WORKSPACES = 8` + `evictWorkspacesIfNeeded()`（LRU：`temporary` 优先淘汰，同优先级按 `lastAccessMillis`）；所有取用入口改为 `touchWorkspace()` 以刷新时间戳 |
| B3 | `AppLog.add` | 共享的 `SimpleDateFormat` 在 `synchronized(lock)` **之外**调用 `format()`；它内部持有可变 `Calendar`，非线程安全 | MCP 并发处理请求时时间戳会串味，甚至抛 `ArrayIndexOutOfBoundsException` —— 而这个异常恰好发生在「写日志」这条路径上，会把真正要记录的错误盖掉 | 格式化与入队合并进同一把锁（开销可忽略） |
| B4 | Android `org.json` 的 `optString` 语义 | `optString(key)` 对 `JSONObject.NULL` 返回的是**字符串 `"null"`** 而不是 null，于是 `optString(k).ifBlank { null } ?: JSONObject.NULL` 这类兜底**永远不会触发** | 报告里出现字面量 `"null"`；涉及 `patch_report.asm`、Blutter registry 的 `reason` / `dartVersion` / `snapshotHash`、`frida_call` 的 JS 参数等 10 余处 | 新增 `core/JsonText.kt`：`JSONObject.optText` / `optNonBlankText` + `JSONArray.optText` / `optNonBlankText`（缺失 / JSON null / 空串统一收敛为 null），替换全部失效兜底 |
| B5 | `Storage.readSource` | 条件分支里**先**无条件走 `RootShell.readBytes()`，**后**才轮到 `File.readBytes()` —— 顺序反了 | `/data/app`、`/system`、`/apex` 下的 `.so` 通常是 `0644`：直读实测 23ms，而 `su -c cat` 要 fork 一次 su（实测 139ms）；SU 通道还是串行的，并发 `so_open` 时就是瓶颈 | 改为「先直读并核对长度 → 失败或长度不符再回退 root」 |
| B6 | `temporary` 参数 | 只在 `workspace_overview` 里被回显，**没有任何清理逻辑读取它**；而且本来就不存在跨重启持久化机制，schema 那句「won't persist across restarts」既无法兑现也无法违背 | 误导性 API：调用方以为 `temporary=true` 能省内存，实际不省（叠加 B2 就是坑） | 语义改为「disposable：达到 8 个上限时优先淘汰」，并据此真正接入 B2 的 LRU |
| B7 | `PatchByteUtils.byteDiffRanges` | 逐字节扫描，每个差异区间 new 一个 `JSONObject`，**无数量上限**；三个调用点只有 Rizin 那条有 `<=1MB` 保护 | 正常时没事；LIEF 重建若整体平移偏移，两个几百 MB 数组会产出海量区间 → 堆被打爆 + 响应体几百 MB | 改为 `diffRanges(a, b, maxRanges = 256)` 返回 `ByteDiffResult(ranges, truncated, diffBytes)`；三个调用点全部接入并输出 `diffTruncated` / `diffBytes` |
| B8 | `PatchAudit.applyVerify` | `var minSize` 声明为 `var` 却从未重新赋值 | 仅编译器警告，但会淹没真正有价值的警告 | 改 `val` |
| B9 | `LocatorParser.target` | `substringBeforeLast('@')` 在 locator 不含 `@` 时返回整串（Kotlin 隐式语义），当前调用点全靠这个隐式行为 | 不是 bug，但是**没有显式契约的危险依赖**：将来出现含 `@` 的 locator 形态会被静默截断 | 显式写出 `lastIndexOf('@')` 分支，行为完全不变但不再依赖隐式规则 |

**实测证据**

| 项 | 验证结果 |
| --- | --- |
| B1 | `edit_asm(mode=nop_out, byteLength=6)` → `SIZE_MISMATCH`「Selected range 6B is not a multiple of the 4-byte instruction size for arm64」+ `badValue{alignment:4}`；合法写法 `byteLength=8`、`instructionCount=2` 均成功 |
| B2 | 连续 `so_open` 9 个不同 SO → `so_close(action=list)` 的 `count` 正好 **8**，最早打开的 `ld-android.so` 被淘汰，再用其 `workspaceId` 调用 → `WORKSPACE_NOT_FOUND` |
| B3 | 格式化进锁（并发缺陷难以稳定复现，以代码审查 + 编译零警告为准） |
| B4 | `flutter_blutter(action=packages)` 输出 140KB，字符串形式的 `"null"` 出现 **0 次**（修复前会出现 `"dartVersion":"null"` 之类） |
| B5 | `/system/lib64/*.so`（`0644`）直读成功；`/data/local/tmp`、`/data/adb` 下的 root-only 文件回退 root 成功 |
| B7 | 两个 10KB SO 做 `rz_diff` → `diffRangeCount=256`（正好上限）、`diffTruncated=true`、`diffBytes=3254` |

**实测中另外发现的一条限制（非本轮引入）**

- **root 通道对其他应用的私有目录不可用**：KernelSU 的 `su` 域跨不过 SELinux MLS category，
  `su -c test -e /data/user/0/<other-pkg>/...` 会失败，于是 `resolveLocalSoSource` 判为「不存在」，
  `so_open` 报 `SO_NOT_FOUND`。
  - 对照实测：同一份文件放在 `/data/local/tmp` ✅、`/data/adb` ✅、`/system/lib64` ✅ 都能打开，
    **唯独其他 app 的私有目录 ✗**。
  - 影响：从别的 app 内部 dump 出来的 so 若留在对方私有目录，会得到误导性的「path not found」。
  - 规避：先把文件复制到 `/data/local/tmp` 再打开。

### 第三轮：Flutter 全链路实测（2026-11-07）

针对"Flutter 程序到底能不能分析"做端到端实测（某 Flutter 应用 + 5 个 Flutter 应用），
发现 `flutter_blutter(action=analyze)` **在任何输入上都 100% 失败**，并定位到两层原因。

| 编号 | 位置 | 是什么 | 影响什么 | 修法 |
| --- | --- | --- | --- | --- |
| F1 | `SoReverseApplication.onCreate` | runner 进程声明为 `isolatedProcess="true"`；隔离进程里 SharedPreferences 不可用，而 `onCreate` 无条件构造 `SettingsStore` | **runner 启动约 0.85s 即崩**，`analyze` 在任何设备/任何 APK 上只得到 `RUNNER_CRASHED`；Blutter AOT 能力整体不可用 | `onCreate` 开头 `if (Process.isIsolated()) return` |
| F2 | `AndroidManifest.xml` | 即使跳过 Application 初始化，隔离进程的 SELinux 域仍让 runner 在 `blutter_run_fd` 入口 SIGSEGV（`fault addr 0xffffffffffffffff`） | runner 依旧不可用 | 移除 `android:isolatedProcess="true"`，改为普通 `:blutter` 独立进程（崩溃仍不影响主进程） |
| F3 | `BlutterCoordinator.prepareInput` / `inspect` | ABI split 安装时 `libapp/libflutter` 不在 `base.apk` 内，直接判 `FLUTTER_LIBS_NOT_FOUND` | so 就在同目录 `lib/<abi>/` 下却分析不了 | 自动回退同级目录；并处理安装目录用 cpuAbi 简称（`lib/arm64`）而 APK 内是 `lib/arm64-v8a` 的命名差异 |
| F4 | `EngineRuntimeRead.outline` | 只查 ELF 符号表，stripped 二进制 `symbols=0` → 任何 locator 都 `FUNCTION_NOT_FOUND` | `analyze_outline` 对绝大多数生产 SO 不可用，且与 schema 描述不符 | 按 ELF 符号 → Rizin 恢复函数解析，响应新增 `resolvedBy` |
| F5 | `FLUTTER_VERSION_NOT_SUPPORTED` | 只给 supported/required 两组数据，调用方要自己对比才知道缺什么 | 不可操作 | 新增 `missingRunner`（可直接拿去构建）+ 说明为何不能运行时下载 + 可操作 nextActions |
| F6 | `RUNNER_INTERRUPTED` / `RUNNER_CRASHED` 文案 | 仍写 "isolated runner process"，只给一句"进程断开" | 误导排查方向 | 说明真实成因（Blutter 自身 Dart 类型断言 / 内存），指向 crash log |

**实测证据**

| 项 | 验证结果 |
| --- | --- |
| F1 | 修复前 crash_report：`SharedPreferences cannot be accessed if UserManager is not available`，进程 0.85s 死亡 |
| F2 | 修复后 `uid is 10380`（不再是隔离 uid 99040），runner 真正执行到 Dart 解析阶段 |
| F3 | ProxyPin 的 `base.apk`（split）从 `FLUTTER_LIBS_NOT_FOUND` → `running` |

**关于"增量支持所有新旧 Flutter"**（完整讨论见 `11.Flutter与Blutter.md`）

- 兼容单位是 `snapshotHash`（一个 hash 覆盖多个 Flutter 版本），需要的 runner 数量远小于版本总数；
- runner 必须随 APK 分发（`dlopen` 只能命中 APK 的 native lib 目录；Android 10+ 禁止从可写目录加载）；
- 可行路径：**按需构建** / 多产物 APK / 多版本 runner 合并进单个 `.so`。

### 第四轮：Blutter 引擎按需下载（2026-11-07）

**先纠正第三轮的一个错误结论**：当时写的「runner 必须随 APK 分发（Android 10+ 禁止从
可写目录 dlopen）」是错的。Android 限制的是外部存储那类「其他方可能篡改」的位置；
**应用自己的 `files/` 目录是可以 `dlopen` 的** —— 由 `myfler/fler-dart` 实证
（`files/engines/` 下 32 个 `dartvm_<ver>.so`，`targetSdk=36` 正常工作，实测 388 MB）。

| 编号 | 位置 | 内容 |
| --- | --- | --- |
| G1 | `blutter_bridge.cpp` | 支持**绝对路径** dlopen：`/` 开头 → 形式校验（`.so` 结尾、无 `..`、字符白名单）后直接加载；否则维持库名 + namespace 搜索 |
| G2 | `engine/BlutterEngineStore.kt`（新增） | 本地 runner 存放与发现：扫 `files/blutter-engines/dartvm_<dartVersion>.so`，或读 `runners.local.json`（`libraryName` 可只写文件名；**sha256 不符即拒绝加载**） |
| G3 | `BlutterRunnerRegistry` | 合并内置 + 本地，`runnerId` 撞车内置优先；`capabilities` 暴露 `embeddedRunnerCount` / `localRunnerCount` |
| G4 | `flutter_blutter(action=engines)` | 打印目录路径、已发现的 runner、占用体积与安装方式 |
| G5 | `tools/blutter-matrix/export_engines.py`（新增） | 把既有构建产物导出成按需下载布局（`dartvm_*.so` + `runners.local.json` + `engines-manifest.json`） |
| G6 | `.github/workflows/blutter-engines.yml`（新增） | 手动触发构建引擎包，可只构建指定 Dart 版本（临时收窄 `curated-versions.json`），可选发布为 Release |

**实测证据**

| 项 | 验证结果 |
| --- | --- |
| G1+G2+G3 | 把内置 runner 复制成 `files/blutter-engines/dartvm_3.11.5.so` → `engines` 动作报告 `local-dart-3_11_5-arm64-v8a`；某 Flutter 应用（Dart 3.11.5）的 `analyze` 从 `FLUTTER_VERSION_NOT_SUPPORTED` 变为 **选中 local runner 并 `running`**，`libraryName` 是绝对路径 |
| 加载确实发生 | 同一作业随后报 `RUNNER_NATIVE_FAILED`（runner 内部 abort），而**不是** `Cannot load Blutter runner` —— 证明绝对路径 dlopen 已成功、代码已执行 |
| 覆盖度 | `curated-versions.json` 现有 8 个版本（`3.11.5 / 3.12.2 / 3.13.0 / 3.13.1` + 4 beta），正是本机实测遇到的那批 |

**结论**：Blutter 的多版本覆盖不再是「必须重建 APK」，而是「按需下载一个约 12.6 MB 的
引擎包」；覆盖设备上全部 Flutter 应用只需 2–3 个版本。

**第二层：APK 审计四件套此前全部失真（三处字节解析错误 + 一处 Int 溢出）**

| 编号 | 位置 | 内容 |
| --- | --- | --- |
| H1 | `ApkSigTools.readEntry` | ZIP 条目的 deflate 是 **raw deflate**，`Inflater()` 默认 `nowrap=false` 会找 zlib 头并抛 `incorrect header check`，被 catch 成 `null` ⇒ **所有压缩条目都读不出来**。改 `Inflater(true)` |
| H2 | `ApkSigTools.abiCoverage` | `2 * 1024 * 1024 * 1024` 声明为 `Int` 溢出成负数 ⇒ 一个 SO 都不解析。签名改 `Long`；顺带把「首字节 0x7F」弱判据换成完整 ELF magic |
| H3 | `ApkSigTools.signerBlocks` | 漏读 v2/v3 block value 最外层的 `uint32 signersSeqLen` ⇒ signer 起点整体错 4 字节，`parseSigner` 切完 signedData 就用尽缓冲区直接 `return null`。这是 `certCount:0` / `signers:[]` 的唯一原因 |
| H4 | `ApkSigTools.parseSigner` | digest / signature 记录是 `len \| algId \| innerLen \| data` 四段式，旧实现从 `+8` 切到 `+4+len`，把 `innerLen` 拼进了数据前面 ⇒ digest `expected` 多 4 字节前缀、RSA 签名多 4 字节前缀 |
| H5 | `ApkSigTools` 常量 | `DIGEST_CHUNKED_SHA256/SHA512` 从 `0x0301/0x0302` 订正为规范值 **`0x0103/0x0104`**（旧值让 digest 从不参与比对，且把 `0x0103` 误当 DSA 算法） |
| H6 | `ApkSigTools.abiCoverage` | SONAME 冲突检测未按 ABI 分组 ⇒ 任何多 ABI 的 APK 都误报 `soname X maps to multiple sizes`。键改 `"$abi/$soname"` |

签名覆盖范围经 openssl 对真实 APK 双向实测确认是**裸 signed data**（不加长度前缀）：
bare → `Verified OK`，prefixed → `bad signature`。

**第三层：ELF 审计四个真 bug（H7–H10）**

| 编号 | 位置 | 内容 |
| --- | --- | --- |
| H7 | `ElfAudit.bytesForVaddr` | 要求「请求窗口完整落在文件内」才返回数据，而调用方传的是**上界**（DT_GNU_HASH 512 KiB、DT_HASH 64 KiB），真实哈希表往往只有几十字节 ⇒ `elf_hash_tables` 在有 `DT_GNU_HASH` 的 SO 上报 `hasGnu:false`。改为按上界处理（截到文件尾、至少 4 字节可读） |
| H8 | `ElfAudit.paddingCaves` | 只跳过 `SHT_NULL/SHT_NOBITS`，把 `.dynsym` 的 62 段 19 字节零值、`.dynamic`、`.got`、`.got.plt`、`.rela.*`、`.eh_frame`、`.data` 全报成「可 patch 空洞」。新增 `NON_CAVE_SECTION_TYPES` / `NON_CAVE_SECTION_NAMES` + `isStructuralSection()`（类型 + 节名前缀双判据） |
| H9 | `ImportAttribution` | `DT_VERNEED` 的常量写成了 `0x6FFFFFFF`，而那是 **`DT_VERNEEDNUM`**，正确值 `0x6FFFFFFE` ⇒ `parseVerneed` 恒空 ⇒ `mode` 恒为 `needed_heuristic`、所有导入归到第一个 `DT_NEEDED` 库。另加 `SymbolInfo.tableIndex` 字段（`ElfModels.kt` / `ElfParser.kt`），用 dynsym 的**原始下标**查 versym —— 旧代码用过滤后的列表下标，符号一被筛掉就整体错位 |
| H10 | `StringDecryptor.findBlobs` | 只排除 `.dynstr`/`.shstrtab`，把 `.eh_frame` 等结构性节当密文候选。新增结构性节排除 + `SCAN_MIN_BYTES = 10` / `SCAN_MIN_ENTROPY = 3.5` 扫描门槛 |

### 第六轮：MCP 传输层两个规范违规（2026-11-08）

**现象**：SOMCP 进程活着、HTTP 200、81 个工具全部正常响应，但 MCP 客户端报
`MCP client <uuid> is not connected`，工具调用通道整体不可用。

**排查**：这个报错来自客户端侧，所以先把「服务端」和「客户端会话」分开验证。
用 `curl` 直接打 `127.0.0.1:8000/mcp` 拿到 200，说明服务端没问题；再查两处规范细节，
两个都违反：

| 编号 | 位置 | 问题 | 修法 |
| --- | --- | --- | --- |
| M1 | `McpHttpServer.dispatch` / `handleJsonRpcPost` | `initialize` 响应**没有** `Mcp-Session-Id` 头。规范要求服务端签发、客户端后续回传；拿不到 id 的客户端无法区分「会话活着」和「会话没了」 | 新增 `Sessions`：`initialize` 签发 UUID（客户端已带则沿用）、每个请求刷新 `lastSeen`、TTL 1h + 上限 64 条 LRU 淘汰、未见的 id 宽松采纳而不 404 |
| M2 | `McpHttpServer` `get("/mcp")` · `get("/sse")` | 用 `respondText(...)` 回 SSE，产出的是**完整响应**（`Content-Length: 75`）并在写完立刻关闭。客户端发这个请求是为了订阅服务端推送，拿到瞬间 EOF 会读作「连接掉了」 | 新增 `respondSse()`：`respondTextWriter(ContentType.Text.EventStream)` 进入循环，每 10s `": keep-alive\n\n"` + `flush()`；并发上限 8 条，超出 503 |

**同轮补的规范项**：`DELETE /mcp` → `204 No Content` 并移除该会话 id。

**实测对照**

| 项 | 修前 | 修后 |
| --- | --- | --- |
| `initialize` 响应头 | 无 `Mcp-Session-Id` | `Mcp-Session-Id: b01f02a3-…` |
| `GET /mcp`（Accept: text/event-stream） | `Content-Length: 75`，立即 EOF | `Transfer-Encoding: chunked`，25s 内收到 2 条 `: keep-alive` |
| 带会话 id 调 `tools/list` | — | `200` |
| 未见的会话 id | — | `200`（宽松采纳） |
| `DELETE /mcp` | 无此路由 | `204` |
| `GET /sse`（旧版握手） | `Content-Length: 75`，立即 EOF | `chunked` + `event: endpoint` 握手帧 + keep-alive |

**顺带确认的一件无关事**：排查期间发现 NP Manager 的 MCP 服务端返回
`{"code":403,"message":"MCP server is not enabled"}` —— 那个 App 的 MCP 开关没开，
和 SOMCP 无关。已把「如何区分服务端 bug 与对方 App 未启动」写进
`18.错误码与排障.md`。

2. 改动后用 `--rerun-tasks` 编译，并验证 dex 里真的有新代码
3. 改 native 代码要删 `app/.cxx`
4. 新增错误码要在 `guarded` 里加分支，并同步 `18.错误码与排障.md`

### 改文档时

| 改动类型 | 要更新 |
| --- | --- |
| 功能改动 | 对应编号文档 + 本文档「变更记录」 |
| 加/删工具 | `03.工具目录与分类.md` 的清单与总数 + `README.md` |
| 改设置项 | `16.设置项参考.md` |
| 改错误码 | `18.错误码与排障.md` |
| 改构建流程 | `17.构建与CI.md` |
| 一轮改动结束 | 本文档的「变更记录」 |

### Git 约定

- 提交信息用中文，格式 `<type>: <描述>`
- 类型：`feat` / `fix` / `docs` / `chore` / `refactor`
- 大范围改动先只提交本地，推送等用户发话
- 标签按仓库已有序列递增，不拿 APK 的 `versionName` 当标签名
